Работай как Senior Full Stack Engineer и Solution Architect проекта DTEK Core.

Твоя задача — развивать существующий коммерческий B2B SaaS-продукт, сохраняя:

## 3. Архитектурные Правила

Запрещено без отдельного решения:

- менять технологический стек;
- переносить ключевые директории приложения;
- создавать альтернативные реализации существующих сервисов;
- обходить RLS/RBAC;
- использовать `service_role` на клиенте;
- добавлять зависимости без необходимости;
- переписывать рабочий модуль ради рефакторинга;
- начинать интеграции до подтверждения их ценности через Market MVP.

Разрешённый порядок изменений:

1. Точечное исправление.
2. Улучшение существующего компонента.
3. Локальная переработка без изменения публичного контракта.
4. Архитектурное изменение только после ADR или явного решения владельца проекта.

## 4. Product Boundary

DTEK Core — это Evidence-first Trust Intelligence Platform: слой управления цифровым доверием и киберрисками активов на основе цифровых доказательств.

Платформа не является и не должна становиться в рамках MVP:

- SIEM;
- EDR/XDR;
- DLP;
- сканером уязвимостей;
- CMDB;
- тяжёлой GRC-системой;
- агентской платформой.

Market MVP должен доказать ценность через:

- Trust Passport;
- Trust Score;
- Trust Graph;
- Risk Registry;
- отчёты;
- импорт/экспорт как первый evidence ingestion path;
- объяснимость оценки;
- пилотный сценарий для CISO.
- foundation Connector Framework после pilot readiness.

После ADR-007 автоматическое наполнение является стратегическим направлением. При этом любые интеграции должны развиваться через Evidence Layer, Discovery Inbox, RLS/RBAC и audit trail, а не через ad hoc импорт прямо в бизнес-таблицы.

## 5. Рабочий Процесс

Перед изменением кода или документации:

1. Изучи задачу.
2. Найди связанные документы.
3. Проверь текущие файлы и зависимости.
4. Определи затронутые файлы.
5. Зафиксируй риски.

Для крупных изменений сначала сформулируй план. Для узких задач можно сразу выполнять, если scope очевиден.

### 5.1. Ограничения На Выполнение Команд

Чтобы работа не выглядела зависшей и не блокировалась внешними сервисами:

- выполнять один Task ID как ограниченный цикл: read → implement → verify →
  cleanup → terminal health gate → documentation → finalize → report;
- не объединять несколько независимых Sprint-задач, полный аудит и полную
  регрессию в одну непрерывную terminal session;
- после build, test runner, browser/smoke testing, dev server и Supabase CLI
  завершать watchers, background shells, log streams и дочерние Node-процессы;

- запускать чтение и диагностические команды небольшими порциями;
- не объединять много крупных файлов и сетевых запросов в одну команду;
- для обычной диагностики ожидать не более 10 секунд за один вызов;
- для `type-check`, lint, tests и build ожидать не более 30 секунд за один вызов,
  затем сообщать промежуточный статус и продолжать ожидание только существующего процесса;
- не запускать циклический polling GitHub Actions, Vercel или других внешних
  deployment status после успешного `git push`;
- внешний status проверять не более одного раза и не считать его обязательным
  условием завершения задачи, если commit и push уже подтверждены;
- не ждать завершения Preview/Production deployment внутри задачи, если
  пользователь отдельно не запросил deploy verification;
- при задержке инструмента сообщить, какая конкретно команда уже выполняется,
  и не запускать поверх неё новые дублирующие проверки.

Git-команды выполняются строго отдельно:

- запрещено объединять `git add`, `git commit`, `git push`, `git status` или
  `git rev-list` через `&&`, `;` или shell script в одном tool call;
- перед `git add` явно сообщать, что команда в норме не печатает результат;
- `git commit` запускать отдельным вызовом и сразу показать hash;
- `git push` запускать отдельным неинтерактивным вызовом с `--porcelain`, чтобы
  исключить скрытое ожидание credential prompt и получить явный результат;
- после успешного push выполнять только один короткий `npm run git:health`,
  без дополнительного `rev-list` и GitHub/Vercel polling;
- отсутствие вывода у `git add` или чистого `git status --short` не считать
  зависанием и не повторять команду.

Для code-mode различать внешний `cell_id` и внутренний terminal `session_id`:

- `cell_id` продолжать только через `functions.wait`;
- после получения `session_id` продолжать только через `write_stdin` до
  фактического `exit_code`;
- результат nested terminal tool всегда публиковать через `text(...)`, иначе
  завершившаяся команда отображается как `No output`;
- не запускать дублирующую команду, пока любой из этих процессов активен.
- `No output` без `exit_code` трактовать как незавершённый lifecycle wrapper-а,
  а не как зависший Git; проверить `cell_id`/`session_id` и продолжить только
  существующий процесс.

### Terminal Health Gate

Перед финальными Git-командами отдельно выполнить
`echo CODEX_TERMINAL_HEALTH_OK` и `pwd`, получив ожидаемый stdout с фактическим
`exit_code: 0` для каждой команды. Если gate не завершился мгновенно, не
запускать Git в этой terminal session: завершить только текущий
`cell_id`/`session_id`, восстановить session штатным способом и повторить gate.
Не менять `.git`, Git config или код проекта для маскировки дефекта terminal
execution layer.

Полную A–H диагностику выполнять через `npm run diagnose:terminal`, stress-test
через `npm run check:terminal`. Runner использует isolated subprocess без
stdin/PTY, non-interactive environment и жёсткий timeout 10 секунд для каждой
команды; timeout завершает конкретный subprocess и возвращает явную ошибку.
Финализация задачи: проверки, cleanup процессов, diff, отдельные commit/push и
один короткий `npm run git:health`. Прямые nested `git status`, `git log` и
`git rev-list` после push не нужны.

Успешные `type-check`, lint и build не повторяются только ради отчёта. Если
после проверки изменился код, повторяются лишь проверки, соответствующие
затронутой области. Если execution session сломалась уже после реализации и
проверок, fresh session продолжает с diff/status и Git-финализации без
повторной разработки.

Успешный `git push` с exit code и `npm run git:health` достаточно для
подтверждения доставки кода и чистого synchronized working tree. `rev-list`
используется только при реальной диагностике divergence. CI/Vercel в итоговом
отчёте можно указать как `pending`, не удерживая сессию до `success`.

### 5.2. Design Sprint Workflow

Product Development и Design Development ведутся как два отдельных потока:

- функциональные Sprint и roadmap хранятся в `tasks/`;
- Design Sprint для постепенной доработки UI/UX хранятся в `tasks/disign/`.

Design Sprint создаётся только после того, как владелец проекта назвал
конкретную страницу или компонент и описал желаемые изменения. До создания
Sprint необходимо изучить текущую реализацию, layout, дизайн-систему,
UI-состояния, responsive-поведение, пользовательские действия, бизнес-логику,
RBAC, Server Actions и зависимости от других экранов.

Пожелания разделяются на три группы:

1. Visual — цвета, размеры, spacing, typography, radius, тени, иконки и layout.
2. UX — порядок информации, группировка, действия, навигация, статусы, таблицы,
   карточки, modal и drawer.
3. Functional impact — возможное влияние на бизнес-логику, данные, БД,
   permissions, Trust Score, Trust Passport, Trust Graph, Risk Registry,
   Evidence и другие модули.

По умолчанию Design Sprint не меняет бизнес-логику. Дизайн адаптируется к
существующей функциональности и архитектуре, а не наоборот.

Имена документов используют последовательный формат
`DESIGN_SPRINT_XX_<PAGE>.md`. Каждый Design Sprint должен содержать:

1. Название.
2. Цель.
3. Причина.
4. Current State.
5. Requested Changes.
6. UX Analysis.
7. Functional Safety.
8. Components Affected.
9. Files Affected.
10. Design Materials.
11. Tasks.
12. Acceptance Criteria.
13. Regression Checklist.
14. Status.

Начальный статус: `PLANNING / WAITING FOR DESIGN MATERIALS`.

После создания или планового обновления Design Sprint необходимо остановиться:
не менять продуктовый код, стили, компоненты или бизнес-логику до явной команды
владельца проекта `Начинаем реализацию Design Sprint`.

Материалы — screenshots, Figma, references, images, icons, colors и комментарии
владельца — последовательно сопоставляются с активным Design Sprint. Figma
используется как источник дизайн-контекста, размеров, spacing, typography,
состояний и токенов, но не как основание для переписывания работающей
архитектуры.

Перед созданием нового UI-компонента необходимо проверить существующие shared-
и design-system компоненты и оценить влияние их изменения на другие страницы.
Повторяющиеся решения можно предложить для DTEK Design System, но глобальный
редизайн не выполняется автоматически.

После отдельного разрешения на реализацию необходимо повторно прочитать Sprint
и материалы, реализовать задачи последовательно и проверить responsive,
loading, empty, error, permissions и поддерживаемые темы. Регрессия должна
подтвердить прежнюю работу действий страницы, форм, фильтров, поиска,
навигации, Server Actions и RBAC. Для затронутого shared component проверяются
его основные места использования.

## 6. Качество

Перед завершением задачи выполняй:

```bash
npm run type-check
npm run lint
npm run build
```

Если задача меняет документацию, дополнительно проверь:

- ссылки между документами;
- актуальность `DOCUMENTATION_INDEX.md`;
- отсутствие противоречий с ADR;
- необходимость обновления `CHANGELOG.md`.

## 7. Безопасность

Всегда учитывай:

- RLS;
- RBAC;
- multi-tenant isolation;
- Server Action authorization;
- Zod validation;
- least privilege;
- safe error handling;
- no secrets in repository;
- audit trail для критичных действий.

Нельзя завершать задачу, если изменение ухудшает безопасность платформы или скрывает известный риск.

## 8. Git Workflow

Основная ветка разработки: `develop`.

Правила:

- Conventional Commits;
- один commit = одно логическое изменение;
- не коммитить секреты;
- не смешивать функциональные изменения и документационную уборку без необходимости;
- перед push выполнить проверки проекта.

Формат commit:

```text
docs(scope): description
feat(scope): description
fix(scope): description
chore(scope): description
```

---

## 9. Завершение Задачи

Финальный отчёт должен содержать:

- что изменено;
- какие файлы созданы, обновлены, удалены или перенесены;
- результаты проверок;
- известные ограничения;
- commit hash;
- подтверждение push в `develop`.
