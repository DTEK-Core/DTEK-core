## 1. Общая информация

Данный документ определяет полный порядок реализации MVP DTEK Core через структуру Epic. Каждый Epic представляет собой крупный самостоятельный блок функциональности, который можно доставить пользователю как единое целое.

**Принципы формирования бэклога:**
- Epic сортируются по порядку реализации с учётом технических зависимостей
- Более ранний Epic не должен зависеть от более позднего
- Там, где возможно, Epic могут разрабатываться параллельно (Epics 6, 7, 9)
- Каждый Epic завершается рабочей, тестируемой функциональностью

**Связанные документы:**
- `ARCHITECTURE_DECISIONS.md` — архитектурные решения (ADR-001 — ADR-005)
- `docs/product/User_Stories.md` — 46 пользовательских историй с Acceptance Criteria
- `docs/architecture/Trust_Score_Model_v2.md` — модель расчёта Trust Score
- `docs/architecture/Configurator_Concept_Final.md` — концепция Конфигуратора
- `docs/architecture/Database_Design_Full.md` — полная схема БД

## 4. Epic 1 — Foundation

### Цель

Создать техническую основу проекта: настроить рабочее окружение, инициализировать репозиторий, создать структуру проекта, развернуть базу данных и автоматизировать процесс доставки.

### Бизнес-ценность

Epic не создаёт пользовательской ценности напрямую, но является обязательным условием для всех последующих Epic. Качество Foundation определяет скорость разработки и стабильность продукта на всём протяжении MVP.

### User Stories

Пользовательских историй нет. Epic технический.

### Состав работ

| Задача | Описание |
|---|---|
| Git Repository | Инициализировать репозиторий, создать ветки `main` и `develop`, настроить `.gitignore` |
| Next.js Setup | Создать проект Next.js 14 с App Router, TypeScript (strict mode), ESLint |
| Tailwind + Shadcn/UI | Настроить Tailwind CSS, установить и инициализировать Shadcn/UI |
| Supabase Project | Создать проект Supabase Cloud, получить ключи API |
| Database Migrations | Создать все миграции согласно `Database_Design_Full.md` (10 таблиц) |
| Environment Config | Настроить `.env.local`, `.env.example`, документировать переменные |
| CI/CD Pipeline | Настроить GitHub Actions: lint → type-check → тесты → deploy to Vercel |
| Project Structure | Создать структуру папок: `app/`, `components/`, `lib/`, `types/` |
| CLAUDE.md | Создать корневой файл CLAUDE.md с контекстом проекта для AI-разработки |

### Зависимости

**Входящие:** нет
**Исходящие:** все остальные Epic

### Критерии завершения

- [ ] Репозиторий создан на GitHub, ветки `main` и `develop` настроены
- [ ] Проект Next.js запускается локально командой `npm run dev` без ошибок
- [ ] TypeScript в режиме strict: `npm run type-check` завершается без ошибок
- [ ] Все 10 таблиц созданы в Supabase с RLS-политиками, индексами и ограничениями
- [ ] CI/CD pipeline успешно деплоит на Vercel при push в ветку `develop`
- [ ] Файл `.env.example` документирует все обязательные переменные окружения
- [ ] `CLAUDE.md` создан и содержит стек, структуру проекта, ссылки на ключевые документы

### Оценка

**3–4 рабочих дня** (1 разработчик)

## 5. Epic 2 — Authentication

### Цель

Реализовать полный цикл аутентификации пользователей: регистрацию, подтверждение email, вход, выход и сброс пароля. Настроить защиту маршрутов и middleware авторизации.

### Бизнес-ценность

Аутентификация — входная точка в продукт. Без неё невозможна ни одна другая функция. Качественный UX регистрации и входа формирует первое впечатление о платформе и напрямую влияет на конверсию новых пользователей.

### User Stories

| ID | Название |
|---|---|
| US-001 | Регистрация нового аккаунта |
| US-002 | Вход в систему |
| US-003 | Выход из системы |
| US-004 | Сброс пароля |

### Состав работ

| Задача | Описание |
|---|---|
| Landing Page | Публичная страница продукта с CTA-кнопками Войти / Регистрация |
| Register Flow | Форма регистрации → Email подтверждение → создание профиля |
| Login Flow | Форма входа → JWT сессия → редирект на Dashboard |
| Logout | Аннулирование сессии, редирект на Login |
| Password Reset | Форма запроса → email → форма нового пароля |
| Auth Middleware | Next.js middleware: защита всех `/app/*` маршрутов |
| Auth Guard | Хук `useUser()` для client-side защиты компонентов |
| Error States | Понятные сообщения об ошибках (неверные данные, не подтверждён email, заблокирован) |

### Зависимости

**Входящие:** Epic 1 (Foundation — Supabase Auth должен быть настроен)
**Исходящие:** Epic 3, все последующие

### Критерии завершения

- [ ] Пользователь может зарегистрироваться, получить письмо, подтвердить email и войти
- [ ] Неподтверждённый email блокирует вход с понятным сообщением
- [ ] Неверный пароль/email не раскрывает, что именно неверно
- [ ] Сброс пароля через email работает, ссылка истекает через 1 час
- [ ] Все маршруты `/app/*` перенаправляют неавторизованного пользователя на `/login`
- [ ] После выхода все защищённые маршруты недоступны (refresh token аннулирован)
- [ ] Заблокированный пользователь не может войти

### Оценка

**3–5 рабочих дней** (1 разработчик)

## 6. Epic 3 — Organizations

### Цель

Реализовать создание организаций — основного тенанта системы. Обеспечить возможность создания профиля организации, первичного онбординга через мастер (Configurator Phase 1) и переключения между несколькими организациями.

### Бизнес-ценность

Организация — корневая сущность продукта. Все данные (объекты, риски, граф) принадлежат организации. Качество онбординга определяет, получит ли пользователь ценность в первые 10 минут работы с продуктом.

### User Stories

| ID | Название |
|---|---|
| US-010 | Создание организации |
| US-011 | Просмотр профиля организации |
| US-012 | Редактирование профиля организации |
| US-013 | Работа с несколькими организациями |
| US-090 | Прохождение мастера первичной настройки |

> **Примечание:** US-090 (Configurator Phase 1 — Onboarding Wizard) включается в этот Epic, поскольку мастер запускается сразу после создания организации и является частью флоу создания.

### Состав работ

| Задача | Описание |
|---|---|
| Create Organization | Форма создания, назначение роли Owner, создание `trust_factor_config` |
| Onboarding Wizard | 5-шаговый мастер первичной настройки (Phase 1 из `Configurator_Concept_Final.md`) |
| Organization Profile | Страница профиля с редактированием для Owner |
| Multi-org Switcher | Переключение между организациями, список с ролями и индексами доверия |
| Organization Context | React Context для хранения активной организации, RLS-совместимость |
| Auto-create Records | При создании организации: `trust_factor_config` с дефолтными весами |

### Зависимости

**Входящие:** Epic 2 (Authentication — пользователь должен быть авторизован)
**Исходящие:** Epic 4 (User Management), Epic 5 (Object Management), Epic 11 (Configurator Phase 2)

### Критерии завершения

- [ ] Новый пользователь после первого входа видит экран создания организации
- [ ] Мастер первичной настройки (5 шагов) запускается автоматически после создания
- [ ] После прохождения мастера пользователь попадает на Dashboard с базовой структурой
- [ ] Создавший пользователь получает роль `owner`
- [ ] Автоматически создаётся `trust_factor_config` с весами по умолчанию
- [ ] Профиль организации доступен для просмотра всем участникам
- [ ] Редактирование профиля доступно только Owner
- [ ] Пользователь может переключаться между несколькими организациями

### Оценка

**3–4 рабочих дня** (1 разработчик)

## 7. Epic 4 — User Management

### Цель

Реализовать полный цикл управления командой организации: создание и доставку приглашений, принятие приглашений, назначение ролей, блокировку и удаление участников. Обеспечить принудительное соблюдение RBAC-матрицы (ADR-003).

### Бизнес-ценность

Управление командой — обязательное условие для B2B-продукта. Организации работают командами, а не в одиночку. RBAC обеспечивает безопасность данных и соответствие корпоративным политикам разграничения доступа.

### User Stories

| ID | Название |
|---|---|
| US-020 | Просмотр списка участников |
| US-021 | Приглашение пользователя |
| US-022 | Принятие приглашения |
| US-023 | Изменение роли участника |
| US-024 | Блокировка участника |
| US-025 | Удаление участника |

### Состав работ

| Задача | Описание |
|---|---|
| Users List Screen | Таблица участников: имя, email, роль, команда, статус, последняя активность |
| Invite Flow | Форма с email и ролью → запись в `invitations` → manual invite link для trusted delivery |
| Accept Invitation | Страница `/invite/{token}` → регистрация/вход → добавление в организацию |
| Role Management | Выпадающий список ролей, валидация (нельзя снять последнего Owner) |
| Block User | Блокировка с аннулированием сессий, подтверждение |
| Remove User | Удаление с предупреждением о последствиях |
| RBAC Middleware | Server-side проверка роли для каждой защищённой операции |
| Invitation Expiry | Cron или lazy-check: истечение приглашений через 7 дней |

### Зависимости

**Входящие:** Epic 3 (Organizations — организация должна существовать)
**Исходящие:** Epic 5 (Object Management — роли влияют на доступные операции)

### Критерии завершения

- [ ] Owner может пригласить пользователя с ролью analyst/admin/viewer
- [ ] Owner видит manual invite link и может передать её адресату; invited user может принять её с регистрацией или входом
- [ ] Принятое приглашение добавляет пользователя с правильной ролью
- [ ] Истёкшее приглашение отклоняется с понятным сообщением
- [ ] Owner может изменить роль любого участника (кроме снятия себя как последнего Owner)
- [ ] Заблокированный пользователь немедленно теряет доступ (сессии аннулированы)
- [ ] Удалённый пользователь не имеет доступа; его объекты/риски сохраняются с owner = NULL
- [ ] RBAC: все защищённые операции проверяются на сервере, не только на клиенте

### Оценка

**4–5 рабочих дней** (1 разработчик)

## 8. Epic 5 — Object Management

### Цель

Реализовать управление цифровыми объектами организации — основными сущностями цифровой модели. Обеспечить полный CRUD для всех типов объектов, просмотр списка с фильтрами и детальный экран объекта.

### Бизнес-ценность

Объекты — фундамент всей платформы. Без объектов невозможны паспорта доверия, риски и граф. Качество UX управления объектами определяет, насколько легко пользователь построит цифровую модель своей организации.

### User Stories

| ID | Название |
|---|---|
| US-030 | Просмотр списка объектов |
| US-031 | Создание объекта |
| US-032 | Редактирование объекта |
| US-033 | Удаление объекта |
| US-034 | Просмотр деталей объекта |
| US-035 | Архивирование объекта |

### Состав работ

| Задача | Описание |
|---|---|
| Objects List Screen | Таблица + карточный вид, фильтры по типу и уровню доверия, поиск, сортировка |
| Create Object Form | Форма с валидацией: название, тип, описание, владелец, критичность, IP, платформа, сегмент, экспозиция |
| Edit Object | Форма редактирования, все поля, пересчёт Trust Score при изменении критичности |
| Delete Object | Подтверждение, каскадное удаление: паспорт, связи, история |
| Archive Object | Статус `archived`, исключение из активных расчётов |
| Object Detail Screen | 5 вкладок: Обзор / Факторы / Риски / Связи / История |

### Зависимости

**Входящие:** Epic 3 (Organizations), Epic 4 (User Management — RBAC по ролям)
**Исходящие:** Epic 6 (Trust Passport), Epic 7 (Risk Registry), Epic 9 (Trust Graph)

### Критерии завершения

- [ ] Пользователь видит список объектов с фильтрами по типу и уровню доверия
- [ ] Поиск по названию и ID работает
- [ ] Доступно переключение между табличным и карточным видом
- [ ] Аналитик ИБ может создавать объекты всех типов
- [ ] Администратор может создавать только инфраструктурные объекты (проверяется на сервере)
- [ ] При создании объекта автоматически создаётся запись в `trust_passports`
- [ ] Детальный экран объекта содержит 5 вкладок
- [ ] Удаление объекта удаляет паспорт, связи и историю Trust Score
- [ ] Архивированные объекты исключены из расчётов и скрыты по умолчанию

### Оценка

**5–7 рабочих дней** (1 разработчик)

## 9. Epic 6 — Trust Passport

### Цель

Реализовать экран цифрового паспорта доверия для каждого объекта — основного артефакта платформы. Паспорт предоставляет исчерпывающее представление об объекте: уровень доверия, факторная разбивка, риски, реквизиты и история. Добавить экспорт в PDF.

### Бизнес-ценность

Trust Passport — главная "продающая" функция продукта. Это то, что отличает DTEK Core от простого реестра активов. Качественный паспорт создаёт ощущение "цифрового двойника" объекта и является главным артефактом для аудитов и отчётности.

### User Stories

| ID | Название |
|---|---|
| US-040 | Просмотр паспорта доверия |
| US-041 | Понимание факторов доверия |
| US-042 | История изменений паспорта |
| US-043 | Экспорт паспорта в PDF |

### Состав работ

| Задача | Описание |
|---|---|
| Passport Screen | Полный экран паспорта согласно дизайн-прототипу (screens_trust.jsx) |

## 11. Epic 8 — Trust Score Engine

### Цель

Реализовать автоматический расчёт Trust Score по взвешенной 6-факторной модели (ADR-001, `Trust_Score_Model_v2.md`). Обеспечить хранение факторных оценок, истории изменений и триггерный пересчёт при изменении данных объекта, рисков или весов организации.

### Бизнес-ценность

Trust Score — центральная метрика платформы. Без его корректного расчёта все данные — просто реестр. Именно Trust Score трансформирует список активов в живую модель доверия. Прозрачность и обоснованность расчёта является ключевым конкурентным преимуществом DTEK Core.

### User Stories

| ID | Название |
|---|---|
| US-050 | Просмотр Trust Score объекта |
| US-051 | Понимание что влияет на Trust Score |
| US-052 | История Trust Score |

### Состав работ

| Задача | Описание |
|---|---|
| Score Calculation Logic | Supabase Edge Function: реализация формулы из `Trust_Score_Model_v2.md` |
| Factor Calculation | Расчёт каждого из 6 факторов из рисков по категориям |
| Criticality Base Values | Low=80, Medium=75, High=70, Critical=65 — базовые значения факторов |
| Risk Penalty Application | Штрафы: Low=-5, Med=-15, High=-25, Crit=-40 по категории риска |
| Completeness Bonus | Расчёт полноты паспорта, бонус +10/+20 к фактору `compliance` |
| Org Index Calculation | Взвешенное среднее Trust Score организации с учётом критичности объектов |
| Recalculation Triggers | DB Triggers → pg_notify → Edge Function при изменении objects/risks/relations/weights |
| Score History Storage | Запись в `trust_score_history` с `factors_snapshot` (JSON) |
| History Endpoint | API: получение истории Trust Score объекта за период |
| Score Chart Component | График динамики Trust Score на экране деталей объекта |
| Org Trust Ring | Обновление индекса организации в `organizations.trust_score` |

### Зависимости

**Входящие:** Epic 6 (Trust Passport — хранит факторные оценки), Epic 7 (Risk Registry — риски влияют на факторы)
**Исходящие:** Epic 10 (Dashboard — использует агрегированный индекс), Epic 11 (Configurator Phase 2 — настройка весов)

### Критерии завершения

- [ ] Trust Score рассчитывается автоматически по формуле из `Trust_Score_Model_v2.md`
- [ ] Все 6 факторных оценок рассчитываются корректно из категорий рисков
- [ ] Базовые значения факторов зависят от критичности объекта
- [ ] Риски в статусе accepted/mitigated/closed не влияют на расчёт
- [ ] Бонус за полноту паспорта применяется к фактору `compliance`
- [ ] Trust Score пересчитывается автоматически при изменении объекта, риска или связи
- [ ] История изменений хранится в `trust_score_history` с `factors_snapshot`
- [ ] Организационный индекс доверия пересчитывается при изменении объектов
- [ ] Граф на экране деталей объекта отображает динамику Trust Score

### Оценка

**4–5 рабочих дней** (1 разработчик)
