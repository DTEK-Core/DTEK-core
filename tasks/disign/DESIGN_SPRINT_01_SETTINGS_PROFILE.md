# DESIGN SPRINT 01 — Settings / Profile

`Статус: PLANNING / WAITING FOR DESIGN MATERIALS`

## 1. Название

Постепенная UI/UX-доработка страницы «Настройки», вкладка «Профиль».

## 2. Цель

Подготовить и согласовать улучшенный визуальный вариант профиля пользователя в
Figma, затем после отдельного разрешения аккуратно перенести утверждённый дизайн
в существующий DTEK Core без изменения продуктовой логики.

## 3. Причина

Владелец проекта выбрал вкладку «Профиль» как первую область отдельного Design
Development потока. Конкретные визуальные и UX-проблемы будут фиксироваться
поэтапно во время ручного редактирования макета и обсуждения вариантов.

## 4. Current State

- Маршрут `/settings` является Server Component и требует аутентифицированного
  пользователя с организацией.
- Заголовок страницы: «Настройки»; подзаголовок: «Управление профилем,
  организацией и платформой».
- Layout состоит из вертикальной навигации шириной 200 px и контентной области
  с максимальной шириной 760 px; ниже 800 px колонки складываются вертикально.
- Вкладка «Профиль» открывается по умолчанию в локальном client-state.
- Карточка профиля содержит аватар с инициалами и пометкой «Скоро», имя, роль,
  команду и форму.
- Редактируются полное имя и поле «Должность / Команда».
- Email отображается как read-only и не меняется без отдельной процедуры
  верификации.
- Кнопка сохранения имеет pending-состояние; успешное сохранение подтверждается
  toast-сообщением, серверная ошибка показывается внутри формы.
- Loading-состояние страницы реализовано через settings skeleton.
- Отдельного empty-состояния у профиля нет: пустое имя не допускается
  валидацией, команда может быть пустой.
- В исходном прототипе `design/src/screens_admin.jsx` присутствуют также кнопка
  изменения фото и поле телефона, но в работающем продукте эти возможности не
  реализованы и не должны возвращаться только ради визуального соответствия.

## 5. Requested Changes

- Работать над вкладкой «Настройки → Профиль» отдельным Design Sprint.
- Владелец проекта самостоятельно редактирует макет и сообщает о внесённых

- Не менять продуктовый код до явной команды на реализацию Design Sprint.

## 6. UX Analysis

Вкладка должна ясно разделять идентификационные данные пользователя, неизменяемые
атрибуты и редактируемые поля. Основное действие сохранения должно оставаться
заметным, но не конкурировать с навигацией Settings. Любая новая компоновка
должна сохранять понятность read-only email, роли пользователя и pending/error/
success feedback.

Решения для desktop необходимо сразу оценивать на узком viewport: вертикальная
навигация уже складывается над контентом, а двухколоночная форма не должна
создавать горизонтальный scroll или слишком узкие поля.

## 7. Functional Safety

Нельзя нарушить:

- authentication и redirect на `/login`;
- проверку наличия организации и redirect на onboarding;
- tenant isolation и действующие RLS-политики;
- обновление только профиля текущего пользователя;
- `UpdateProfileSchema` и ограничения длины полей;
- read-only поведение email;
- отображение фактической роли пользователя;
- pending, success и safe error feedback;
- `revalidatePath('/settings')` и обновление данных App Shell;
- доступ owner/admin к журналу аудита и видимость вкладок по RBAC;
- работу остальных вкладок Settings.

Изменение фото, телефона, email, пароля, 2FA или иных данных является отдельной
функциональной задачей и не входит в этот Sprint без отдельного согласования.

## 8. Components Affected

Потенциально, после утверждения дизайна:

- `SettingsPage` — только композиция заголовка и Settings layout;
- `SettingsLayout` — навигация и контейнер вкладки;
- `ProfileTab` — визуальная структура профиля и формы;
- общие Card, Button, Input и feedback-паттерны — только после проверки всех
  мест использования;
- settings loading skeleton — если утверждённая геометрия контента изменится.

## 9. Files Affected

Предполагаемые файлы реализации, окончательный список определяется после
утверждения Frame:

- `app/(app)/settings/page.tsx`;
- `components/shared/settings/settings-layout.tsx`;
- `components/shared/settings/profile-tab.tsx`;
- `components/shared/loading/page-skeleton.tsx`;
- `app/globals.css`.

Файлы `lib/actions/settings.ts`, `lib/validation/schemas.ts`, Supabase migrations
и database types не должны меняться для чисто визуальной итерации.

## 12. Acceptance Criteria

- Утверждённый Frame визуально воспроизведён без изменения бизнес-логики.
- Имя и команда редактируются и сохраняются как раньше.
- Email явно воспринимается как неизменяемое поле.
- Роль пользователя отображается корректно.
- Pending, success и error состояния понятны и доступны.
- Keyboard focus видим; labels связаны с соответствующими controls.
- Desktop и mobile не имеют наложений и горизонтального scroll.
- Навигация всех Settings tabs остаётся доступной.
- Визуальные решения соответствуют существующей тёмной DTEK design system.
