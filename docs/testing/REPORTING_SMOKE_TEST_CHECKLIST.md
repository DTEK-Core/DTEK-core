## Назначение

Этот документ — ручной чеклист проверки готовности модуля **Reporting & Export**.

Цель проверки: убедиться, что Sprint 10 работает целостно:

- Trust Passport report открывается и сохраняется как PDF;
- Risk Registry CSV скачивается с учётом фильтров;
- Executive Organization Report открывается и сохраняется как PDF;
- RBAC не даёт лишнего доступа;
- audit events фиксируют export-сценарии;
- empty/error states понятны пользователю;
- интерфейс работает на desktop и mobile без критичных визуальных проблем.

Если во время проверки найден дефект, зафиксируйте его в разделе **Журнал замечаний** или заведите отдельный bug report по шаблону [BUG_REPORT_TEMPLATE.md](BUG_REPORT_TEMPLATE.md).

## Подготовка

### 1. Локальная Среда

1. Убедитесь, что `.env.local` настроен и Supabase доступен.
2. Запустите приложение:

```bash
npm run dev
```

3. Откройте:

```text
http://localhost:3000
```

4. Откройте DevTools:
   - Console — для ошибок JavaScript;
   - Network — для проверки HTTP-статусов и скачивания CSV.

### 2. Тестовые Роли

Для полного теста нужны аккаунты:

| Роль | Назначение |
|---|---|
| `owner` | Полная проверка всех отчётов и audit log |
| `analyst` | Проверка разрешённого export-доступа |
| `admin` | Проверка запрета bulk export и доступа к audit log |
| `viewer` | Проверка read-only поведения |

Рекомендуемый способ: разные браузеры или разные профили Chrome.

Если непонятно, как получить аккаунты с разными ролями, используйте [RBAC_TESTING_GUIDE.md](RBAC_TESTING_GUIDE.md). Коротко: первый зарегистрированный пользователь организации получает роль `owner`; затем owner создаёт invite-ссылки в `/users` для `analyst`, `admin` и `viewer`. Не регистрируйте эти роли через `/register`, иначе они станут owner отдельных организаций и проверка RBAC будет некорректной.

### 3. Тестовые Данные

В тестовой организации должно быть:

- минимум 3 активных объекта;
- минимум 1 объект с низким или критическим Trust Score;
- минимум 3 риска:
  - 1 `critical` + `open` или `in_progress`;
  - 1 `high`;
  - 1 закрытый или принятый риск;
- минимум 1 риск, привязанный к объекту;
- включённый доступ к `/settings` для owner/admin, чтобы проверить audit log.

Если данных нет, сначала создайте их через UI:

1. `/objects` → добавить объекты.
2. `/risks` → создать риски.
3. `/objects/[id]` → привязать риски к объектам.
4. `/dashboard` → убедиться, что KPI и топ рисковых объектов не пустые.

- [ ] Все P1-сценарии прошли со статусом `PASS`.
