## Подготовка

1. Убедитесь, что локальный сервер запущен:
   ```bash
   npm run dev
   ```
   Откройте http://localhost:3000 в браузере Chrome или Safari.

2. Откройте DevTools (Cmd+Option+I или F12) → вкладка **Console**.
   В Console не должно быть красных ошибок.

3. Держите DevTools открытым на **Network**, чтобы видеть HTTP-запросы и заголовки.

4. Подготовьте тестовую учётную запись:
   - **owner-аккаунт**: вы, владелец тестовой организации
   - **analyst-аккаунт**: второй браузер/профиль (для проверки RBAC)
   - **viewer-аккаунт**: третий браузер/профиль инкогнито

5. В тестовой организации должно быть минимум **3 объекта** и **3 риска** для проведения полного тестирования.

## Шаг 1: Security Headers

**URL:** http://localhost:3000/dashboard

**Что делать:**
1. Откройте DevTools → вкладка **Network**
2. Перейдите на /dashboard (или обновите страницу)
3. Кликните на первый запрос `dashboard` в списке
4. Перейдите на вкладку **Response Headers**

**Проверочный лист:**
- [ ] `x-frame-options: DENY` — присутствует
- [ ] `x-content-type-options: nosniff` — присутствует
- [ ] `referrer-policy: strict-origin-when-cross-origin` — присутствует
- [ ] `permissions-policy: camera=(), microphone=(), geolocation=(), payment=()` — присутствует
- [ ] `content-security-policy` — присутствует и содержит `frame-ancestors 'none'`

**Если все заголовки на месте** → Security Headers работают корректно ✓

## Шаг 2: Dashboard — KPI и Trust Score организации

**URL:** http://localhost:3000/dashboard  
**Роль:** owner

**Что проверять:**
- [ ] Страница открывается без ошибок в Console
- [ ] В шапке экрана: заголовок «Дашборд» или «Dashboard»
- [ ] **KPI-карточки** видны: количество объектов, активных рисков, Trust Score организации, критических рисков
- [ ] **Org Trust Ring** — кольцо с числовым значением Trust Score (0–100) в центре
- [ ] **Топ рисковых объектов** — 3–5 объектов с наименьшим Trust Score, кликабельны
- [ ] **График тренда** — Trust Score за 30 / 90 / 365 дней (переключатель периода)
- [ ] **Лента событий** — последние изменения в платформе

**Тест действия:**
1. Запомните текущий Trust Score организации (в KPI-карточке)
2. Перейдите в /risks → добавьте новый `critical` риск к одному из объектов
3. Вернитесь на /dashboard
4. **Ожидаем:** Trust Score организации снизился

## Шаг 5: Trust Graph — создание связи

**URL:** http://localhost:3000/graph  
**Роль:** owner

**Что делать:**
1. Кликните по объекту A — откроется боковая панель
2. В разделе «Связи» нажмите «Добавить связь»
3. Выберите: Тип связи=`использует`, Целевой объект=объект B
4. Нажмите «Создать»

**Ожидаемый результат:**
- [ ] Ребро (линия) появляется между узлами A и B на графе
- [ ] Тип связи подписан или указан стрелкой
- [ ] Связь сохранена (после обновления страницы ребро остаётся)

**Попытка создать дублирующую связь:**
1. Снова добавьте связь A → B того же типа
2. **Ожидаем:** Ошибка «Связь уже существует»

## Шаг 9: Trust Passport — полная проверка

**URL:** http://localhost:3000/objects/[id]/passport  
**Роль:** owner

**Подготовка:** Убедитесь, что объект имеет минимум 1 риск.

**Что проверять:**

### Trust Ring
- [ ] Кольцо заполнено пропорционально Trust Score
- [ ] Числовое значение Score в центре кольца
- [ ] Цвет кольца соответствует уровню доверия

### Факторная разбивка
- [ ] 6 факторов видны: Уязвимости, Конфигурация, Доступы, Сегментация, Соответствие, Инциденты
- [ ] Для каждого: числовой балл (0–100) и вес в процентах
- [ ] Сумма (вес_i × балл_i) / 100 = Trust Score объекта (допускается погрешность ±1)

### Реквизиты объекта
- [ ] Название, Тип, Критичность, IP-адрес, Платформа, Сегмент сети

### История изменений
- [ ] Список записей об изменениях Trust Score
- [ ] Каждая запись: дата, старый Score, новый Score, причина

## Шаг 10: Trust Score Engine — проверка пересчёта

**Тест 1: Добавление риска снижает Score**
1. Запомните Trust Score объекта (назовём X)
2. Добавьте новый риск с категорией `vulnerability`, критичностью `critical`
3. Откройте паспорт объекта
4. **Ожидаем:** Trust Score < X

**Тест 2: Закрытие риска повышает Score**
1. Запомните текущий Trust Score (назовём Y)
2. Измените статус добавленного риска на `resolved`
3. Откройте паспорт объекта
4. **Ожидаем:** Trust Score > Y (или вернулся к X)

**Тест 3: Граница 0–100**
1. Добавьте 5+ рисков с критичностью `critical` к одному объекту
2. Откройте паспорт
3. **Ожидаем:** Trust Score ≥ 0 (не уходит ниже нуля)

## Шаг 11: Конфигуратор — базовый тест

**URL:** http://localhost:3000/configurator  
**Роль:** owner

**Что проверять:**
- [ ] 6 полей/слайдеров с весами факторов
- [ ] Текущая сумма весов = 100%
- [ ] Названия факторов совпадают с паспортом объекта

**Тест — изменение весов:**
1. Запомните Trust Score одного объекта
2. Значительно измените веса: например, `Уязвимости` с 22% на 40%, `Соответствие` с 16% на 0%, `Конфигурация` с 18% на 16% (добейтесь суммы = 100%)
3. Нажмите «Сохранить»
4. Откройте паспорт объекта
5. **Ожидаем:** Trust Score изменился (пересчитан с новыми весами)

**Тест — валидация суммы:**
1. Установите веса так, чтобы сумма ≠ 100% (например, 95%)
2. Нажмите «Сохранить»
3. **Ожидаем:** Ошибка «Сумма должна быть 100%», сохранения нет

**Тест — сброс:**
1. Нажмите «Сбросить к умолчаниям»
2. **Ожидаем:** vuln=22%, config=18%, access=18%, network=14%, compliance=16%, incident=12%

## Шаг 17: Реестр рисков — полный обход

**URL:** http://localhost:3000/risks  
**Роль:** owner

**Что проверять:**
- [ ] Таблица рисков с колонками: Название, Объект, Категория, Критичность, Статус, Дедлайн
- [ ] Фильтр по статусу (`open`, `in_progress`, `resolved`) — работает
- [ ] Фильтр по критичности (`critical`, `high`, `medium`, `low`) — работает
- [ ] Поиск по названию — работает

**Жизненный цикл риска:**
1. Создайте новый риск (статус `open`)
2. Измените на `in_progress` → Trust Score объекта пересчитывается (может не изменяться, только `resolved`)
3. Измените на `resolved` → Trust Score объекта пересчитывается вверх
4. Удалите риск → Trust Score должен вернуться к значению без риска

## Шаг 19: E2E-сценарий — аналитик ИБ работает с платформой

Пройдите полный пользовательский сценарий от лица аналитика ИБ:

1. **Войдите** как owner в тестовую организацию
2. **Откройте Dashboard** → запомните организационный Trust Score
3. **Перейдите в /objects** → создайте новый сервер:
   - Название: `Prod Web Server`
   - Тип: `server`
   - Критичность: `critical`
   - IP: `10.0.0.1`
4. **Откройте паспорт** созданного объекта → убедитесь в начальном Trust Score
5. **Добавьте риск** через /risks:
   - Название: `CVE-2024-0001 — SQL Injection`
   - Категория: `vulnerability`
   - Критичность: `critical`
   - Объект: `Prod Web Server`
   - Дедлайн: через 7 дней
6. **Вернитесь в паспорт** → Trust Score снизился
7. **Откройте /graph** → найдите узел `Prod Web Server`
8. **Создайте связь**: Prod Web Server `использует` → другой сервер в организации
9. **Перейдите в /configurator** → поднимите вес `Уязвимости` до 30%, скорректируйте другие → сохраните
10. **Проверьте паспорт** → Trust Score пересчитан с новыми весами
11. **Откройте /settings → Журнал аудита** → убедитесь, что событие `config.weights_changed` записано
12. **Вернитесь в /dashboard** → организационный Trust Score изменился относительно шага 2

**Ожидаемый результат:** Все шаги выполнены без ошибок, данные корректны.
