# PILOT_OFFER.md — DTEK Core

`Sprint: S09-T007`  
`Статус: актуальный`  
`Дата: 22.08.2026`
`Назначение: 14-дневное pilot offer для первых CISO и ИБ-команд`

---

## 1. Краткое Предложение

Первый пилот DTEK Core:

> За 14 дней собрать цифровую карту доверия 50–200 ключевых активов, показать Trust Score организации и топ-10 рисков, сильнее всего влияющих на безопасность.

Пилот проверяет не полноту enterprise-внедрения, а ключевую ценность Market MVP:

```text
Активы -> риски -> Trust Score -> Trust Graph -> executive insight
```

---

## 2. Для Кого

Пилот подходит компании, если выполняются 4+ признака:

- есть CISO, руководитель ИБ или IT-директор как владелец пилота;
- есть 50–200 важных или критичных активов;
- есть 20–100 известных рисков, замечаний, findings или проблем;
- активы и риски сейчас ведутся в Excel, Confluence, Jira, Service Desk, GRC-light или вручную;
- нужно быстро показать руководству состояние безопасности;
- есть боль приоритизации: непонятно, что исправлять первым;
- компания готова использовать реальные или обезличенные данные;
- SaaS-формат допустим для пилота или возможна работа на обезличенном dataset.

## 3. Что Получает Клиент

| Результат | Описание |
|---|---|
| Demo/Pilot organization | Организация в DTEK Core с данными клиента или обезличенным dataset |
| Trust Passport | Паспорт доверия для ключевых активов |
| Trust Score | Оценка доверия 0–100 по активам и организации |
| Risk Registry | Риски с привязкой к объектам и приоритетами |
| Trust Graph | Карта критичных связей и зависимостей |
| Top-10 risks | Список рисков, сильнее всего влияющих на доверие |
| Executive snapshot | Итоговая управленческая картина для CISO |
| Next-step recommendation | Что исправлять первым и какие данные нужны дальше |

---

## 4. Что Не Является Целью Пилота

Пилот не обещает:

- заменить SIEM, EDR, DLP, VM, CMDB или GRC;
- автоматически просканировать инфраструктуру;
- внедрить десятки интеграций;
- стать production-системой учёта с первого дня;
- закрыть требования enterprise procurement;
- провести полноценный аудит ИБ;
- подтвердить соответствие регуляторным требованиям;
- выполнить on-prem deployment без отдельного решения.

Пилот отвечает на один вопрос:

> Дает ли DTEK Core CISO более понятную картину доверия, рисков и приоритетов по активам?

## 5. Входные Данные

### 5.1 Минимальный Dataset

| Данные | Минимум | Предпочтительно |
|---|---:|---:|
| Активы | 50 | 100–200 |
| Риски / findings | 20 | 40–100 |
| Владельцы активов | 3–5 команд | По каждому критичному объекту |
| Связи между системами | 10–20 | 30–60 |
| Критичность активов | Да | Да |
| Статусы рисков | Да | Да |

### 5.2 Форматы

В текущем Market MVP допустимы:

- CSV/XLSX import объектов и рисков через встроенный preview/validation flow;
- ручное создание и корректировка записей;
- обезличенный список активов и рисков;
- выгрузка из существующего CMDB/GRC/Service Desk как input-файл.

Важно:

> CSV/XLSX import реализован в Sprint 11 как первый evidence ingestion path. Он работает по create-only модели: массовое обновление существующих записей, полный rollback файла и Connector Framework пока не поддерживаются.

### 5.3 Поля Активов

Желательные поля:

- название;
- тип;
- критичность;
- владелец;
- сегмент;
- exposure;
- краткое описание;
- связи с другими объектами.

### 5.4 Поля Рисков

Желательные поля:

- название;
- описание;
- категория;
- severity;
- probability;
- статус;
- связанный объект или группа объектов;
- владелец риска, если есть;
- срок или SLA, если есть.

## 7. 14-Дневный План

### День 0 — Qualification

Цель: подтвердить, что компания подходит для пилота.

Вход:

- discovery-интервью по [ICP_INTERVIEW_SCRIPT.md](ICP_INTERVIEW_SCRIPT.md);
- score 10+ по scoring rubric;
- владелец пилота со стороны клиента;
- согласие на работу с реальными или обезличенными данными.

Результат:

- pilot scope подтверждён;
- выбран формат данных;
- согласованы дата kickoff и участники.

### День 1 — Kickoff

Цель: зафиксировать бизнес-вопрос пилота.

Обсуждается:

- какие активы считаются ключевыми;
- какие риски уже известны;
- какие сегменты важны;
- какие ограничения по данным;
- что должно быть показано CISO в конце.

Результат:

- список данных;
- роли участников;
- success criteria;
- срок финальной сессии.

### День 2–3 — Data Intake

Цель: получить и нормализовать входные данные.

Работы:

- собрать список активов;
- собрать список рисков;
- выделить критичные объекты;
- определить связи;
- согласовать категории и статусы.

Результат:

- dataset готов к загрузке;
- спорные поля отмечены;
- данные не содержат секретов.

### День 4–5 — DTEK Core Setup

Цель: создать pilot organization и первичную модель доверия.

Работы:

- создать pilot organization;
- настроить роли;
- загрузить, импортировать или вручную завести активы;
- завести риски;
- связать риски с объектами;
- настроить отраслевые веса Trust Score.

Результат:

- объекты и риски видны в DTEK Core;
- Trust Passport доступен для ключевых активов;
- базовый Trust Score рассчитан.

### День 6–7 — Trust Graph & Review

Цель: проверить критичные зависимости.

Работы:

- создать связи между ключевыми активами;
- проверить граф с IT/security owner;
- уточнить связи, которые усиливают риск;
- выбрать 3–5 hero objects для финальной истории.

Результат:

- Trust Graph отражает понятные зависимости;
- выбран demo path для финальной сессии.

### День 8–10 — Analysis

Цель: подготовить управленческие выводы.

Работы:

- проверить объекты с низким Trust Score;
- выделить топ рисков;
- сопоставить риски с критичностью активов;
- сформировать top-10 priorities;
- зафиксировать спорные или неполные данные.

Результат:

- сформирован pilot insight;
- понятны ограничения данных;
- есть предварительный executive snapshot.

### День 11–12 — Client Review

Цель: проверить результат с рабочей группой клиента.

Работы:

- показать Dashboard, Objects, Trust Passport, Risks и Graph;
- собрать корректировки;
- уточнить top-10 risks;
- проверить, что выводы не искажают реальность клиента.

Результат:

- финальный walkthrough подтверждён;
- исправления внесены;
- success criteria готовы к оценке.

### День 13 — Executive Preparation

Цель: подготовить финальную сессию для CISO.

Работы:

- сформировать 5–7 ключевых тезисов;
- подготовить порядок показа;
- выбрать 1–2 критичных цепочки в Trust Graph;
- подготовить next-step recommendations.

Результат:

- финальный сценарий готов;
- команда понимает, какие решения просить у CISO.

### День 14 — Final Session

Цель: показать ценность DTEK Core и принять решение о следующем шаге.

Показывается:

- Trust Score организации;
- топ объектов с низким доверием;
- Trust Passport ключевого актива;
- топ-10 рисков;
- Trust Graph критичной зависимости;
- что исправлять первым;
- что требуется для следующего этапа.

Результат:

- CISO оценивает полезность;
- фиксируются objections;
- принимается решение: stop / iterate / paid pilot / расширенный пилот.

## 8. Success Criteria

Пилот успешен, если выполнены 5+ условий:

- клиент увидел 50–200 активов в единой модели;
- клиент увидел 20–100 рисков с привязкой к активам;
- CISO понял, какие активы имеют низкое доверие;
- команда согласилась с top-10 risk priorities;
- Trust Passport оказался понятным артефактом для обсуждения;
- Trust Graph показал хотя бы одну значимую зависимость;
- итоговый executive snapshot можно показать руководству;
- клиент попросил следующий шаг, расширение данных или повторную встречу;
- подтверждена готовность платить или обсуждать paid pilot.

## 9. Метрики Пилота

| Метрика | Целевое значение |
|---|---:|
| Time to first value | До 1 рабочего дня после загрузки данных |
| Активов в модели | 50–200 |
| Рисков в модели | 20–100 |
| Критичных связей в графе | 10+ |
| Top risks identified | 10 |
| CISO usefulness score | 4/5 или выше |
| Готовность к следующему шагу | Да / нет |

Эта таблица остаётся кратким offer-level summary. Канонические определения,
источники evidence, data completeness, usage, product value, operational
quality, willingness-to-pay ladder, feedback cadence и connector demand model
описаны в [PILOT_METRICS_FEEDBACK_LOOP.md](PILOT_METRICS_FEEDBACK_LOOP.md).

Метрика не получает `PASS` без даты и evidence. Готовность к следующему шагу
уточняется через commitment stage, named owner и decision date, а не только
через положительный отзыв.

## 10. Обязательные Ограничения Безопасности

Для первых пилотов:

- не собирать пароли, токены, ключи и секреты;
- не хранить реальные персональные данные без необходимости;
- использовать обезличивание, если SaaS вызывает вопросы;
- не обходить RLS/RBAC;
- не использовать service role на клиенте;
- не смешивать demo/pilot data с production-клиентами;
- заранее согласовать, какие данные можно показывать в финальной сессии.

Если клиент требует on-prem, сертификацию или формальный enterprise SLA до начала работы, такой сценарий фиксируется как future enterprise requirement, а не как обязательство Sprint 09.

## 12. Decision Outcomes

| Итог | Что означает | Следующий шаг |
|---|---|---|
| Stop | Боль не подтверждена или продукт не подходит | Зафиксировать инсайты |
| Iterate | Ценность есть, но нужны уточнения | Дополнительное интервью или переработка dataset |
| Repeat demo | Есть интерес, но нужен другой stakeholder | Повторная сессия с CISO/IT |
| Paid pilot | Ценность подтверждена | Коммерческое предложение |
| Product gap | Ценность есть, но нужен missing feature | Передать в backlog Sprint 10–15 |
