# Trust Graph Model

## Назначение

Trust Graph представляет организацию в виде графа взаимосвязанных объектов. Каждый объект является узлом графа. Связи между объектами отображаются в виде ребер.

После ADR-007 Trust Graph развивается от ручной карты связей к evidence-backed цифровой модели инфраструктуры.

# Цели

**Trust Graph позволяет:**
- визуализировать структуру организации;
- выявлять критические зависимости;
- анализировать влияние рисков;
- оценивать последствия компрометации объектов;
- понимать распространение угроз.

# Базовые сущности

## Узел (Node)

`Любой объект организации.`

**Примеры:**
- сотрудник;
- сервер;
- ноутбук;
- база данных;
- приложение;
- автомобиль;
- дрон;
- IoT устройство.

## Связь (Edge)

`Отношение между объектами.`

# Типы связей MVP

## Uses

`Использует.`

**Пример:**
- Сотрудник → Ноутбук

## Depends On

`Зависит от.`

**Пример:**
- Приложение → База данных

## Connected To

`Подключен к.`

**Пример:**
- Ноутбук → VPN

## Managed By

`Управляется.`

**Пример:**
- Сервер → Администратор

## Owns

`Владеет.`

**Пример:**
- Организация → Сервер

# Свойства узла

**Каждый узел содержит:**
- ID
- Название
- Тип
- Trust Score
- Критичность
- Статус

# Свойства связи

**Каждая связь содержит:**
- ID
- Тип связи
- Источник
- Назначение
- Дата создания
- Источник данных
- Confidence

# Цветовая индикация

**Высокое доверие:**
- Зеленый

**Среднее доверие:**
- Желтый

**Низкое доверие:**
- Оранжевый

**Критическое состояние:**
- Красный

# Анализ влияния

**Система должна определять:**
- Какие объекты зависят от выбранного объекта.

**Пример:**

`Сотрудник -> Ноутбук -> VPN -> Сервер -> База данных`

Компрометация ноутбука влияет на всю цепочку.

# Основные функции текущего MVP

- создание узла;
- создание связи;
- удаление связи;
- просмотр графа;
- поиск объектов;
- фильтрация объектов.

# Ограничения текущего MVP

- Автоматический анализ атак отсутствует.
- Автоматическое построение графа ещё не реализовано.
- Все связи в реализованном MVP создаются пользователем вручную.

# Evidence-first развитие

В целевой архитектуре связи появляются из:

- network flow;
- IAM / directory services;
- Kubernetes;
- cloud dependencies;
- SIEM/log correlations;
- firewall/VPN logs;
- vulnerability scanner topology;
- ручных корректировок.

Автоматические связи должны иметь source, confidence и возможность подтверждения или отклонения в Discovery Inbox.

Confidence formula, human-only conflict/merge boundaries и review lifecycle
определены в
[Confidence_Engine_Discovery_Inbox.md](../architecture/Confidence_Engine_Discovery_Inbox.md);
автоматическое построение графа по-прежнему не реализовано.

# Будущее развитие

**В будущих версиях система должна:**
- автоматически строить граф из evidence;
- рассчитывать распространение риска;
- моделировать сценарии атак;
- строить карту цифрового доверия организации в реальном времени.
