`Статус: актуальный`

---

## 1. Назначение

Документ фиксирует профиль первого клиента DTEK Core и сценарий интервью для проверки Market MVP.

Цель S09-T004 — подготовить команду к первым разговорам с CISO, руководителями ИБ, IT-директорами и ИБ-интеграторами так, чтобы интервью проверяли реальную боль рынка, а не превращались в презентацию продукта.

DTEK Core в интервью позиционируется как:

> Платформа управления цифровым доверием и киберрисками активов: Trust Passport, Trust Score, Trust Graph и Risk Registry для CISO и команды ИБ.

---

## 2. Research Objective

Главная гипотеза:

> CISO и ИБ-команды в компаниях 100–2000 сотрудников испытывают боль из-за разрозненного учёта активов, рисков, связей и управленческой отчётности. Они готовы рассмотреть лёгкую платформу, которая быстро создаёт trust/risk snapshot без внедрения тяжёлой GRC или CAASM-системы.

Интервью должно проверить:

- есть ли у компании проблема видимости активов и рисков;
- как сейчас формируется картина для руководства;
- хватает ли существующих инструментов;
- понятна ли идея Trust Passport и Trust Score;
- полезен ли Trust Graph как способ объяснить зависимости;
- готова ли компания к 14-дневному пилоту;
- какие требования блокируют SaaS-формат или ранний MVP.

## 3. Primary ICP

### 3.1 Company Profile

| Параметр | Целевой профиль |
|---|---|
| География | Россия |
| Размер | 100–2000 сотрудников |
| IT/ИБ-зрелость | Есть отдельный ответственный за ИБ или выделенная ИБ-функция |
| Инфраструктура | Есть бизнес-критичные IT-активы, удалённый доступ, внутренние сервисы, подрядчики |
| Текущий учёт | Excel, Confluence, Jira, Service Desk, сканеры, CMDB-light или разрозненные списки |
| Боль | Нет единой управленческой картины доверия и рисков по активам |
| Покупатель | CISO, руководитель ИБ, IT-директор, собственник ИБ-процесса |
| Пользователи | Аналитик ИБ, IT-администратор, риск-менеджер, интегратор |

### 3.2 First Adopter Segments

| Сегмент | Почему подходит |
|---|---|
| ИТ/SaaS-компании | Много сервисов, быстрые изменения, нужен понятный risk snapshot |
| Промышленность среднего размера | Есть IT/OT-связи, удалённый доступ, подрядчики, высокий интерес к критичным активам |
| Энергетика вне тяжёлого enterprise | Хорошо раскрывает Trust Graph и отраслевые веса Trust Score |
| Медицинские организации | Есть чувствительные данные и необходимость управленческой отчётности |
| Образовательные организации | Много распределённых систем и ограниченные ИБ-ресурсы |
| ИБ-интеграторы и консалтинг | Могут использовать DTEK Core как repeatable-инструмент обследования клиентов |

## 4. Anti-ICP

DTEK Core не должен на раннем этапе фокусироваться на компаниях, где первый разговор почти гарантированно уйдёт в enterprise procurement, сертификацию или on-prem.

| Профиль | Почему не первый сегмент |
|---|---|
| Крупные банки | Высокие требования к сертификации, SLA, on-prem, интеграциям и тендерам |
| Федеральный госсектор | Длинный цикл закупки, регуляторные ограничения, сложная безопасность |
| Крупная КИИ | Требуются on-prem, сертификация, формальные контуры эксплуатации |
| Компании без ИБ-функции | Нет владельца боли и процесса принятия решения |
| Компании с зрелой enterprise GRC/CAASM | Боль может быть закрыта тяжёлыми платформами |
| Команды, ищущие SIEM/EDR/DLP | Продуктовая категория не совпадает с ожиданиями |

## 6. Qualification Criteria

### 6.1 Strong Fit

Компания подходит для первых интервью и пилота, если выполняются 4+ признака:

- есть 50–200 критичных или важных активов;
- риски и активы сейчас ведутся в Excel, Confluence, Jira или вручную;
- CISO регулярно готовит отчёты для руководства;
- есть боль приоритизации: непонятно, что исправлять первым;
- есть удалённый доступ, подрядчики или внешние сервисы;
- есть необходимость связать технические риски с бизнес-критичными объектами;
- компания готова обсуждать ручной или CSV-импорт данных;
- есть владелец пилота со стороны ИБ.

### 6.2 Medium Fit

Компания подходит для интервью, но не обязательно для первого пилота, если:

- активов меньше 50;
- ИБ-процесс пока неформальный;
- есть интерес к теме, но нет срочной боли;
- решение нужно скорее как консалтинг или аудит;
- SaaS возможен только на обезличенных данных.

### 6.3 Low Fit

Пока не приоритет, если:

- компания ищет конкретный технический сенсор;
- главный запрос — импорт из десятков систем с первого дня;
- требуется on-prem до любого демо;
- нет владельца данных по активам и рискам;
- интервьюер не может назвать ни один актуальный риск или критичный актив.

## 7. Interview Format

| Параметр | Рекомендация |
|---|---|
| Длительность | 35–45 минут |
| Формат | Discovery call, не sales demo |
| Участники | 1–2 человека со стороны DTEK Core, 1–3 человека со стороны клиента |
| Запись | Только с явного согласия |
| Демо | 10–12 минут в конце, если боль подтверждена |
| Основной принцип | Сначала процесс и боль, потом продукт |

### Suggested Agenda

| Время | Блок |
|---:|---|
| 0–5 мин | Контекст компании и роль участника |
| 5–20 мин | Текущий процесс учёта активов, рисков и отчётности |
| 20–30 мин | Боли, последствия и критерии ценности |
| 30–40 мин | Короткое демо или концептуальная проверка |
| 40–45 мин | Pilot fit, следующие шаги |

## 8. Interview Script

### 8.1 Opening

Короткое открытие:

> Мы проверяем Market MVP DTEK Core — платформы для цифровых паспортов доверия, Trust Score и карты рисков активов. Нам важно понять ваш текущий процесс: как вы видите критичные активы, риски и состояние безопасности для руководства. Это не продажный звонок, а discovery-интервью.

Обязательные уточнения:

- можно ли делать заметки;
- можно ли записывать звонок;
- можно ли задавать уточняющие вопросы по реальному процессу;
- можно ли в конце показать короткий пример продукта.

### 8.2 Core Questions

| # | Вопрос | Что проверяем |
|---:|---|---|
| 1 | Как у вас сейчас ведётся список критичных IT/ИБ-активов? | Источник данных и зрелость asset inventory |
| 2 | Где сейчас живут риски по этим активам: Excel, Jira, GRC, Service Desk, Confluence, другое? | Фрагментация данных |
| 3 | Как вы определяете, каким активам сейчас можно доверять, а какие требуют внимания? | Наличие или отсутствие trust model |
| 4 | Какие 3–5 факторов больше всего влияют на доверие к активу в вашей организации? | Проверка факторов Trust Score |
| 5 | Как вы сейчас связываете риск с конкретным активом или группой активов? | Ценность Risk Registry |
| 6 | Бывает ли ситуация, когда риск становится критичным из-за связей между системами? | Ценность Trust Graph |
| 7 | Как выглядит отчёт для руководства: какие метрики и выводы туда попадают? | Executive reporting need |
| 8 | Сколько времени уходит на подготовку такого отчёта или security snapshot? | Time-to-value и cost of pain |
| 9 | Что чаще всего мешает быстро понять, что исправлять первым? | Приоритизация и decision support |
| 10 | Какие инструменты уже используются: SIEM, EDR, сканеры, CMDB, GRC, Service Desk? | Ландшафт и границы продукта |
| 11 | Чего не хватает в этих инструментах для управленческой картины? | Дифференциация DTEK Core |
| 12 | Насколько понятна идея Trust Passport для каждого объекта? | Проверка ключевого артефакта |
| 13 | Был бы полезен единый Trust Score 0–100 по активу и организации, если он объясним по факторам? | Проверка Trust Score |
| 14 | Какие данные вы были бы готовы загрузить в 14-дневный пилот: объекты, риски, связи, владельцы? | Pilot readiness |
| 15 | Что должно произойти за 14 дней, чтобы вы сказали: “это стоит продолжать”? | Success criteria |

### 8.3 Optional Follow-Up Questions

Использовать, если есть время или участник даёт сильные сигналы боли.

| Тема | Вопрос |
|---|---|
| Бюджет | Покупаете ли вы сейчас инструменты для ИБ-отчётности, GRC, asset management или posture management? |
| Интеграторы | Пользуетесь ли вы внешними ИБ-консультантами для аудитов или обследований? |
| Регуляторика | Есть ли требования, которые заставляют регулярно показывать состояние активов и рисков? |
| Импорт | Какой формат данных проще всего предоставить для пилота: CSV, Excel, выгрузка из CMDB, ручная таблица? |
| Security | Какие ограничения есть по SaaS, обезличиванию и хранению данных? |
| Procurement | Кто должен подтвердить пилот: ИБ, IT, закупки, юристы, руководство? |

## 9. Expected Signals

### 9.1 Positive Signals

Сильные сигналы market fit:

- участник быстро называет реальные критичные активы;
- риски сейчас ведутся вручную или в нескольких системах;
- отчётность для руководства собирается долго;
- есть боль объяснения приоритетов IT-команде или бизнесу;
- идея Trust Score вызывает вопросы о методологии, а не отторжение;
- Trust Graph воспринимается как способ показать последствия связей;
- участник сам предлагает данные для пилота;
- есть готовность к повторной встрече с коллегами.

### 9.2 Warning Signals

Сигналы, требующие осторожности:

- основной запрос — автоматическое сканирование или SIEM-корреляция;
- участник не видит ценности без интеграций в первый день;
- Trust Score воспринимается как слишком субъективный;
- данные нельзя выгружать даже в обезличенном виде;
- нет владельца процесса по активам и рискам;
- организация требует on-prem до любых обсуждений.

### 9.3 Negative Signals

Слабый fit:

- “у нас всё уже закрыто GRC/CMDB”;
- “нам нужен только сканер уязвимостей”;
- “мы не ведём риски по активам и не планируем”;
- “руководству такие отчёты не нужны”;
- “пилот возможен только после тендера и сертификации”.

## 10. Scoring Rubric

После каждого интервью оценить fit по шкале 0–3.

| Критерий | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| Pain intensity | Боли нет | Боль эпизодическая | Боль регулярная | Боль влияет на решения CISO |
| Data readiness | Данных нет | Данные есть частично | Данные можно собрать вручную | Данные готовы для импорта |
| Buyer access | Нет владельца | Есть пользователь | Есть руководитель ИБ | Есть decision maker |
| Product understanding | Не понял | Понял частично | Понял ценность | Сам сформулировал use case |
| Pilot readiness | Не готов | Возможно позже | Готов обсудить | Готов планировать пилот |

### Interpretation

| Total score | Интерпретация | Действие |
|---:|---|---|
| 0–5 | Low fit | Не переводить в пилот |
| 6–9 | Learning interview | Сохранить инсайты, вернуться позже |
| 10–12 | Qualified prospect | Предложить повторное демо / one-pager |
| 13–15 | Pilot candidate | Переходить к S09-T007 Pilot Offer |

## 11. Demo Trigger

Не показывать демо автоматически в начале звонка. Сначала подтвердить хотя бы 2–3 боли:

- нет единой картины активов и рисков;
- сложно объяснить состояние ИБ руководству;
- непонятно, что исправлять первым;
- риски становятся важнее из-за связей между системами;
- отчётность собирается вручную.

Если боли подтверждены, показать короткий сценарий из [DEMO_NARRATIVE.md](DEMO_NARRATIVE.md):

```text
Dashboard -> Objects -> Trust Passport -> Risks -> Graph -> Configurator
```

Демо должно занимать не больше 10–12 минут и завершаться вопросом:

> Если бы мы загрузили ваши 50–200 ключевых активов и 20–100 рисков, какой результат был бы полезен через 14 дней?
