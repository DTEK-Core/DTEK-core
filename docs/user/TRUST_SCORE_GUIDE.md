# DTEK Core — Руководство по Trust Score

`Версия: 1.0`  
`Дата: 26.06.2026`  
`Аудитория: Аналитики ИБ, CISO`

---

## Что такое Trust Score

**Trust Score** — это числовая оценка уровня доверия к информационному объекту (серверу, приложению, учётной записи и т.д.), выраженная в диапазоне от **0 до 100**.

Trust Score не является статическим рейтингом — это **живая метрика**, которая автоматически пересчитывается при каждом изменении: появлении нового риска, закрытии уязвимости, обновлении данных объекта или изменении весов факторов.

---

## Уровни доверия

| Trust Score | Уровень | Цвет | Интерпретация |
|---|---|---|---|
| 80 – 100 | **High** (Высокий) | Зелёный | Объект надёжно защищён. Незначительные улучшения возможны, но риски минимальны |
| 60 – 79 | **Good** (Хороший) | Сине-зелёный | Приемлемый уровень защищённости. Требует внимания при появлении новых угроз |
| 40 – 59 | **Medium** (Средний) | Жёлтый | Накопились риски. Требуется плановая работа по устранению проблем |
| 20 – 39 | **Low** (Низкий) | Оранжевый | Серьёзные проблемы безопасности. Необходимы срочные меры |
| 0 – 19 | **Critical** (Критический) | Красный | Объект крайне уязвим. Требуются немедленные действия |

---

## Шесть факторов Trust Score

Trust Score рассчитывается по взвешенной сумме **шести независимых факторов**. Каждый фактор отражает отдельный аспект безопасности объекта:

| Фактор | Ключ | Что измеряет | Вес по умолчанию |
|---|---|---|---|
| **Уязвимости** | `vuln` | Число и критичность известных CVE и уязвимостей | **22%** |
| **Конфигурация** | `config` | Соответствие стандартам безопасной конфигурации | **18%** |
| **Доступы** | `access` | Управление привилегиями и учётными записями | **18%** |
| **Сегментация сети** | `network` | Изоляция и контроль сетевого трафика | **14%** |
| **Соответствие ПБ** | `compliance` | Выполнение политик безопасности и требований | **16%** |
| **Инциденты** | `incident` | История инцидентов и время реакции | **12%** |
| | | **Сумма:** | **100%** |

---

## Формула расчёта

```
Trust Score = (
    vuln_score       × vuln_weight +
    config_score     × config_weight +
    access_score     × access_weight +
    network_score    × network_weight +
    compliance_score × compliance_weight +
    incident_score   × incident_weight
) / 100
```

Где:
- `*_score` — оценка фактора от 0 до 100
- `*_weight` — вес фактора в % (сумма = 100)
- Результат округляется до целого числа

---

## Как рассчитывается оценка каждого фактора

Каждая из шести факторных оценок вычисляется по одному алгоритму:

```
factor_score = base − risk_penalty + completeness_bonus
```

Где:
- `base` — базовая оценка по критичности объекта
- `risk_penalty` — суммарный штраф за активные риски
- `completeness_bonus` — бонус за полноту паспорта (только для фактора `compliance`)
- Результат зажат в диапазоне [0, 100]

### Базовая оценка (base)

Начальная точка для каждого фактора определяется критичностью объекта:

| Критичность объекта | Базовая оценка |
|---|---|
| Низкая (low) | 80 |
| Средняя (medium) | 75 |
| Высокая (high) | 70 |
| Критическая (critical) | 65 |

**Логика:** Более критичный объект изначально имеет более низкую базу, потому что к нему применяются более строгие требования безопасности. Даже без единого риска критический объект не получит 100 баллов.

---

## Штрафы за риски

Только риски со статусом `open` или `in_progress` снижают Trust Score. Устранённые (`mitigated`, `accepted`, `closed`) риски не учитываются.

### Размер штрафа по критичности риска

| Критичность риска | Штраф к фактору |
|---|---|
| Критический (critical) | **−40** |
| Высокий (high) | **−25** |
| Средний (medium) | **−15** |
| Низкий (low) | **−5** |

### Привязка категорий рисков к факторам

Каждая категория риска влияет на конкретный фактор Trust Score:

| Категория риска | Фактор | Полное название |
|---|---|---|
| `vulnerability` | `vuln` | Уязвимости |
| `configuration` | `config` | Конфигурация |
| `access` | `access` | Доступы |
| `network` | `network` | Сегментация сети |
| `compliance` | `compliance` | Соответствие ПБ |
| `incident` | `incident` | Инциденты |
| `monitoring` | `incident` | Инциденты (мониторинг как часть реагирования) |
| `organizational` | *(все)* | Влияет на все 6 факторов равномерно |
| `physical` | *(все)* | Влияет на все 6 факторов равномерно |
| `human` | *(все)* | Влияет на все 6 факторов равномерно |
| `other` | *(все)* | Влияет на все 6 факторов равномерно |

**Риски без конкретного фактора** (organizational, physical, human, other) распределяют штраф равномерно: `penalty / 6` на каждый фактор.

---

## Бонус за полноту паспорта

Фактор **Соответствие ПБ** (`compliance`) получает дополнительный бонус, если паспорт объекта хорошо заполнен:

| Полнота паспорта | Бонус |
|---|---|
| ≥ 95% | **+20** к compliance |
| ≥ 80% | **+10** к compliance |
| < 80% | 0 |

**Логика:** Полно заполненный паспорт свидетельствует о хорошей документированности объекта, что само по себе является элементом соответствия политикам безопасности.

---

## Как считается полнота паспорта

Полнота паспорта (completeness_pct) рассчитывается как сумма весов заполненных полей:

| Поле | Вес |
|---|---|
| Название объекта | 15% |
| Описание | 15% |
| Тип объекта | 10% |
| Критичность | 10% (всегда заполнена) |
| Ответственный владелец | 10% |
| IP-адрес / сетевой идентификатор | 10% |
| Платформа / ОС | 10% |
| Сетевой сегмент | 10% |
| Тип экспозиции | 10% |
| **Максимум** | **100%** |

## Организационный Trust Index

Помимо Trust Score отдельных объектов, платформа рассчитывает **организационный Trust Index** — взвешенное среднее Trust Score всех активных объектов.

**Формула:**
```
Org Trust Index = Σ(object.trust_score × criticality_weight) / Σ(criticality_weight)
```

**Веса критичности:**

| Критичность объекта | Вес в индексе |
|---|---|
| Критическая (critical) | **4** |
| Высокая (high) | **3** |
| Средняя (medium) | **2** |
| Низкая (low) | **1** |

**Логика:** Критические объекты влияют на общий индекс сильнее, чем менее важные. Если критический сервер базы данных имеет Trust Score 30, это тянет индекс вниз в 4 раза сильнее, чем офисный ноутбук с таким же Score.

## Примеры расчётов

### Пример 1 — Новый объект без рисков (средняя критичность)

**Параметры:**
- Тип: Сервер (server)
- Критичность: medium
- Полнота паспорта: 60% (заполнены только обязательные поля)
- Активные риски: нет

**Расчёт:**
```
base = 75 (medium)

compliance_bonus = 0 (полнота < 80%)

vuln       = 75 − 0 = 75
config     = 75 − 0 = 75
access     = 75 − 0 = 75
network    = 75 − 0 = 75
compliance = 75 − 0 + 0 = 75
incident   = 75 − 0 = 75

Trust Score = (75×22 + 75×18 + 75×18 + 75×14 + 75×16 + 75×12) / 100
            = (1650 + 1350 + 1350 + 1050 + 1200 + 900) / 100
            = 7500 / 100
            = 75
```

**Результат: Trust Score = 75, уровень Good**

---

### Пример 2 — Объект с критической уязвимостью

**Параметры:**
- Тип: Сервер приложений
- Критичность: high
- Полнота паспорта: 85%
- Активные риски: 1 × critical (категория vulnerability)

**Расчёт:**
```
base = 70 (high)

compliance_bonus = +10 (полнота ≥ 80%)

vuln       = 70 − 40 = 30    ← штраф за critical vulnerability
config     = 70 − 0  = 70
access     = 70 − 0  = 70
network    = 70 − 0  = 70
compliance = 70 − 0 + 10 = 80  ← бонус за полноту паспорта
incident   = 70 − 0  = 70

Trust Score = (30×22 + 70×18 + 70×18 + 70×14 + 80×16 + 70×12) / 100
            = (660 + 1260 + 1260 + 980 + 1280 + 840) / 100
            = 6280 / 100
            = 63
```

**Результат: Trust Score = 63, уровень Good**

> Одна критическая уязвимость снизила Trust Score с ~70 до 63. Видно, что uln-фактор сильно упал (30), но другие факторы остались высокими — общий балл остался приемлемым.

---

### Пример 3 — Объект под массовой атакой

**Параметры:**
- Тип: Сервер баз данных
- Критичность: critical
- Полнота паспорта: 70%
- Активные риски: 1 × critical (vulnerability), 2 × high (access, configuration)

**Расчёт:**
```
base = 65 (critical)

compliance_bonus = 0 (полнота < 80%)

vuln       = 65 − 40 = 25    ← штраф за critical
config     = 65 − 25 = 40    ← штраф за high
access     = 65 − 25 = 40    ← штраф за high
network    = 65 − 0  = 65
compliance = 65 − 0  = 65
incident   = 65 − 0  = 65

Trust Score = (25×22 + 40×18 + 40×18 + 65×14 + 65×16 + 65×12) / 100
            = (550 + 720 + 720 + 910 + 1040 + 780) / 100
            = 4720 / 100
            = 47
```

**Результат: Trust Score = 47, уровень Medium**

> Три риска на критическом сервере дали 47 баллов. При добавлении ещё одного критического риска (incident) Score упадёт в зону Low.

---

### Пример 4 — Эффект от устранения риска

Продолжение Примера 3: аналитик устраняет critical vulnerability (статус → `closed`).

```
vuln       = 65 − 0  = 65    ← штраф снят
config     = 65 − 25 = 40
access     = 65 − 25 = 40
network    = 65 − 0  = 65
compliance = 65 − 0  = 65
incident   = 65 − 0  = 65

Trust Score = (65×22 + 40×18 + 40×18 + 65×14 + 65×16 + 65×12) / 100
            = (1430 + 720 + 720 + 910 + 1040 + 780) / 100
            = 5600 / 100
            = 56
```

**Результат: Trust Score вырос с 47 до 56** — устранение одного критического риска дало +9 пунктов.

## Как влияет изменение весов (Конфигуратор)

Если организация меняет веса факторов в Конфигураторе, это влияет на **все** объекты.

**Сценарий:** Банк решает увеличить вес фактора `compliance` с 16% до 30% за счёт снижения весов других факторов.

Для объекта из Примера 2 (после устранения уязвимости):
```
Старые веса (default):
Trust Score = (70×22 + 70×18 + 70×18 + 70×14 + 80×16 + 70×12) / 100 = 71

Новые веса (compliance 30%):
Trust Score = (70×20 + 70×16 + 70×16 + 70×10 + 80×30 + 70×8) / 100
            = (1400 + 1120 + 1120 + 700 + 2400 + 560) / 100
            = 7300 / 100
            = 73
```

Объект с хорошей полнотой паспорта (которая даёт бонус к compliance) вырастет больше. Объекты с плохой документацией — упадут.

---

## Практические рекомендации

**Для быстрого роста Trust Score:**
1. Устраняйте риски критичности `critical` первыми — штраф −40 снимается мгновенно
2. Заполните паспорт хотя бы на 80% — это даёт +10 к фактору compliance
3. Закрывайте риски, а не только переводите в `in_progress` — штраф снимается только при `mitigated`/`accepted`/`closed`

**Для объективной оценки:**
1. Не скрывайте риски — занижение реестра даёт ложно высокий Trust Score
2. Отражайте реальную критичность объектов — занижение критичности искажает картину
3. Проводите регулярный аудит: закрытые риски, которые не обновляются в системе, не учитываются

**Для настройки под отрасль:**
1. Финансовый сектор: увеличьте вес `compliance` и `access`
2. Производство / АСУ ТП: увеличьте вес `network` и `vuln`
3. Ритейл: увеличьте вес `access` (защита персональных данных)
4. IT-компании: балансируйте `vuln`, `config`, `access` примерно поровну
