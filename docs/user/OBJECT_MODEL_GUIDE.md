# DTEK Core — Модель объектов

`Версия: 1.0`  
`Дата: 12.07.2026`

---

## Что такое объект в DTEK Core

**Объект** — это любой информационный актив организации, безопасность которого нужно отслеживать, оценивать и контролировать.

Объект в DTEK Core — это не просто запись в реестре активов. Это **живая сущность** с:
- собственным **Trust Score** (обновляется автоматически)
- **Trust Passport** (структурированным цифровым паспортом)
- **реестром рисков** (привязанных именно к этому объекту)
- **историей изменений** (каждое изменение Trust Score зафиксировано)
- **связями в Trust Graph** (зависимости от других объектов)
- **source/evidence context** (откуда пришли данные об объекте)

В текущем MVP объект можно создать вручную. В Evidence-first модели объект также может быть импортирован или обнаружен через источник данных, а пользователь подтверждает и уточняет его.

## Типы объектов

DTEK Core поддерживает **11 типов объектов**, охватывающих весь спектр информационных активов современной организации:

### Инфраструктурные объекты

| Тип | Ключ | Примеры |
|---|---|---|
| **Сервер** | `server` | Web-сервер, сервер БД, файловый сервер, контроллер домена |
| **Рабочая станция** | `workstation` | Стационарный компьютер сотрудника |
| **Ноутбук** | `laptop` | Переносное устройство, корпоративный ноутбук |
| **Сетевое устройство** | `network` | Маршрутизатор, коммутатор, межсетевой экран, балансировщик нагрузки |

### Программные объекты

| Тип | Ключ | Примеры |
|---|---|---|
| **Приложение** | `app` | Web-приложение, мобильное приложение, корпоративная система |
| **База данных** | `database` | PostgreSQL, Oracle, MySQL, MongoDB |
| **Сервис** | `service` | Микросервис, API, фоновый процесс, очередь сообщений |

### Специализированные объекты

| Тип | Ключ | Примеры |
|---|---|---|
| **Учётная запись / Удостоверение** | `identity` | Сервисная учётная запись, привилегированный аккаунт, API-ключ, сертификат |
| **Объект АСУ ТП / OT** | `ot` | ПЛК, SCADA, промышленный контроллер, промышленный сенсор |
| **Политика** | `policy` | Документ политики безопасности, регламент, стандарт |
| **Другое** | `other` | Любой актив, не попадающий в другие категории |

## Атрибуты объекта

Каждый объект имеет набор атрибутов, которые определяют его характеристики и влияют на Trust Score.

### Обязательные атрибуты

| Атрибут | Тип | Значения | Влияние на Trust Score |
|---|---|---|---|
| **Название** | Текст | Произвольное | Часть полноты паспорта (+15%) |
| **Тип** | Enum | 11 типов | Часть полноты паспорта (+10%) |
| **Критичность** | Enum | low/medium/high/critical | Определяет базовую оценку |

### Необязательные атрибуты (влияют на полноту паспорта)

| Атрибут | Тип | Значения | Вес в полноте |
|---|---|---|---|
| **Описание** | Текст | Произвольное | +15% |
| **Ответственный владелец** | UUID→Profile | Пользователь системы | +10% |
| **IP-адрес** | Текст | IPv4, IPv6, FQDN | +10% |
| **Платформа/ОС** | Текст | Ubuntu 22.04, Windows Server 2022 | +10% |
| **Сетевой сегмент** | Текст | DMZ, LAN, Production | +10% |
| **Тип экспозиции** | Enum | internal/external/isolated | +10% |

### Критичность (подробно)

| Значение | Смысл | Базовая оценка Trust Score |
|---|---|---|
| `low` | Некритичный актив, сбой не влияет на бизнес | 80 |
| `medium` | Важный актив, сбой создаёт неудобства | 75 |
| `high` | Критически важный, сбой нарушает бизнес-процессы | 70 |
| `critical` | Жизненно важный, сбой останавливает организацию | 65 |

### Экспозиция (подробно)

| Значение | Смысл |
|---|---|
| `internal` | Доступен только из внутренней сети |
| `external` | Доступен из интернета / внешних сетей |
| `isolated` | Изолирован, нет сетевого доступа |

### Статусы объекта

| Статус | Смысл |
|---|---|
| `active` | Объект активен и отслеживается |
| `warning` | Есть предупреждения, требует внимания |
| `risk` | Есть открытые риски |
| `critical` | Критические проблемы |
| `archived` | Объект выведен из эксплуатации (не влияет на Trust Index) |

### Discovery state будущей модели

Отдельно от текущего статуса объекта в будущей Evidence-first архитектуре проектируется состояние обнаружения:

| State | Смысл |
|---|---|
| `discovered` | объект найден автоматически |
| `pending_confirmation` | требуется решение пользователя |
| `verified` | объект подтверждён |
| `manual` | объект создан вручную |
| `merged` | объект объединён с другим |
| `archived` | объект выведен из активной модели |

## Зачем нужна цифровая модель

Традиционный подход к управлению активами — это таблица Excel или CMDB с полями: IP-адрес, тип, ответственный. Такая база данных мертва: она описывает активы, но не отвечает на вопросы безопасности.

DTEK Core строит **живую цифровую модель**, которая:

1. **Знает, что происходит с каждым активом прямо сейчас** — Trust Score обновляется при каждом изменении
2. **Понимает зависимости** — Trust Graph показывает, как компрометация одного объекта влияет на связанные
3. **Документирует историю** — каждое изменение Trust Score зафиксировано с причиной
4. **Говорит языком рисков** — риски привязаны к конкретным объектам, а не висят в общем реестре

## Связи между объектами

Trust Graph строится на **6 типах связей** между объектами:

| Тип | Ключ | Направление | Пример |
|---|---|---|---|
| Использует | `uses` | A → B | Приложение использует базу данных |
| Зависит от | `depends_on` | A → B | Сервис зависит от сервера |
| Подключён к | `connected_to` | A ↔ B | Сервер подключён к коммутатору |
| Управляется | `managed_by` | A ← B | Сервер управляется контроллером домена |
| Владеет | `owns` | A → B | Организация владеет сервером |
| Взаимодействует | `interacts_with` | A ↔ B | Сервис взаимодействует с API |

**Важно:** Нельзя создать связь объекта с самим собой. Каждая пара (A, B, тип связи) уникальна.

## Практические рекомендации

### Что делать в первую очередь

1. **Начните с импорта или критических объектов** — CSV/XLSX, серверы баз данных, контроллеры домена, интернет-доступные сервисы
2. **Установите критичность точно** — не занижайте. Критический сервер с критичностью `low` даст ложно высокий Trust Score
3. **Заполните IP и платформу** — это +20% к полноте паспорта и +10 к Trust Score compliance-фактора
4. **Фиксируйте источник данных** — Manual, CSV/XLSX, AD, Zabbix, MaxPatrol VM и т.д.

### Как моделировать инфраструктуру

**Типовая корпоративная инфраструктура:**

```
[Межсетевой экран (network, critical)] ──connected_to──→
  [Web-сервер (server, high)] ──uses──→
    [Сервер приложений (server, critical)] ──depends_on──→
      [БД PostgreSQL (database, critical)]
        ↑
        └──managed_by── [DBA-аккаунт (identity, critical)]
```

**Типовые объекты малого бизнеса (20–100 сотрудников):**
- Сервер Active Directory / LDAP (critical)
- Почтовый сервер / Microsoft 365 tenant (high)
- Web-сайт / интернет-магазин (high)
- NAS / файловый сервер (medium)
- VPN-сервер (high)
- 5–50 рабочих станций и ноутбуков (low/medium)

### Что не стоит добавлять

- Личные устройства сотрудников, не являющиеся корпоративными активами
- Принтеры и периферия (если к ним нет сетевого доступа и они не несут данных)
- Объекты, которые уже выведены из эксплуатации (добавляйте их сразу со статусом `archived`)

## Экспорт Trust Passport В PDF

Для каждого объекта можно сформировать печатный Trust Passport report.

**Как сформировать отчёт:**

1. Откройте объект в `/objects/[id]`.
2. Перейдите в Trust Passport.
3. Нажмите **PDF**.
4. На странице отчёта нажмите **Сохранить PDF**.

Отчёт содержит реквизиты объекта, текущий Trust Score, факторную разбивку, связанные риски и Source / Evidence Coverage placeholder.

Если объект недоступен или паспорт не найден, платформа покажет безопасное состояние «Отчёт недоступен».

Подробнее: [REPORTS_AND_EXPORT_GUIDE.md](REPORTS_AND_EXPORT_GUIDE.md).
