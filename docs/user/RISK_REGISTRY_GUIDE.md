# DTEK Core — Реестр рисков

`Версия: 1.0`  
`Дата: 12.07.2026`

---

## Что такое риск в DTEK Core

**Риск** — это зафиксированная угроза, уязвимость или проблема безопасности, которая снижает уровень доверия к информационным объектам организации.

В отличие от традиционных реестров рисков (Excel, Jira, Word), риск в DTEK Core:
- **Привязан к конкретным объектам** — понятно, что именно под угрозой
- **Автоматически снижает Trust Score** при создании
- **Автоматически восстанавливает Trust Score** при закрытии
- **Имеет SLA** — систему контроля дедлайнов устранения
- **Поддерживает CVSS** — международный стандарт оценки уязвимостей

## Жизненный цикл риска

```
              ┌──────────────────────────────────────┐
              │                                      │
   Создание   ▼          В работе        Устранён   │
    ────── [open] ──→ [in_progress] ──→ [mitigated] │
              │               │              │       │
              │               │              ▼       │
              │               └──→ [accepted]        │
              │                              │       │
              │               ┌──────────────┘       │
              │               ▼                      │
              └──→──→──→── [closed] ←────────────────┘

Штраф Trust Score активен: open, in_progress
Штраф Trust Score снят:   mitigated, accepted, closed
```

### Описание статусов

| Статус | Значение | Влияние на Trust Score |
|---|---|---|
| `open` | Риск выявлен и зарегистрирован. Работа не начата | **Штраф активен** |
| `in_progress` | Работа по устранению ведётся | **Штраф активен** |
| `mitigated` | Риск снижен: угроза существует, но под контролем | **Штраф снят** |
| `accepted` | Риск принят осознанно: устранение нецелесообразно или невозможно | **Штраф снят** |
| `closed` | Риск полностью устранён | **Штраф снят** |

**Важно:** Trust Score пересчитывается автоматически при каждом изменении статуса.

## Атрибуты риска

### Обязательные поля

| Поле | Тип | Описание |
|---|---|---|
| **Название** | Текст | Краткое описание риска |
| **Категория** | Enum | Тематическая группа риска |
| **Критичность** | Enum | Уровень потенциального ущерба |
| **Статус** | Enum | Текущее состояние риска |

### Рекомендуемые поля

| Поле | Тип | Описание |
|---|---|---|
| **Описание** | Текст | Детальное описание угрозы, вектора атаки, потенциального ущерба |
| **Вероятность** | Enum | Оценка вероятности реализации угрозы |
| **CVSS** | Число 0–10 | Стандартизированная оценка уязвимости |
| **SLA (дней)** | Целое число | Максимальное время на устранение в рабочих днях |
| **Влияние** | Текст | Описание ущерба для бизнеса |
| **Ответственный** | Пользователь | Кто отвечает за устранение |

## Категории рисков

11 категорий покрывают весь спектр угроз информационной безопасности:

### Технические категории

| Категория | Ключ | Что включает | Фактор Trust Score |
|---|---|---|---|
| **Уязвимость** | `vulnerability` | CVE, дыры в ПО, устаревшие версии, нескорректированные патчи | vuln (−40/−25/−15/−5) |
| **Конфигурация** | `configuration` | Небезопасные настройки, дефолтные пароли, лишние сервисы | config |
| **Доступ** | `access` | Избыточные привилегии, слабые пароли, отсутствие MFA | access |
| **Сеть** | `network` | Открытые порты, неправильная сегментация, уязвимый трафик | network |
| **Соответствие** | `compliance` | Нарушение политик безопасности, несоответствие стандартам | compliance |
| **Инциденты** | `incident` | Зафиксированные инциденты безопасности, брутфорс, утечки | incident |
| **Мониторинг** | `monitoring` | Отсутствие логирования, слепые пятна в мониторинге | incident |

### Организационные категории (штраф распределяется по всем 6 факторам)

| Категория | Ключ | Что включает |
|---|---|---|
| **Организационный** | `organizational` | Отсутствие процессов, неудовлетворительная документация |
| **Физический** | `physical` | Физический доступ, кражи оборудования |
| **Человеческий** | `human` | Социальная инженерия, фишинг, ошибки персонала |
| **Другое** | `other` | Риски, не попадающие в другие категории |

## CVSS — Common Vulnerability Scoring System

DTEK Core поддерживает CVSS как дополнительный атрибут риска. CVSS — это международный стандарт оценки серьёзности уязвимостей.

**Когда использовать CVSS:**
- При регистрации CVE (уязвимостей в программном обеспечении)
- При проведении внешнего пентеста или аудита
- Для стандартизации сравнения рисков

**Диапазоны CVSS и соответствующая критичность:**

| CVSS | Критичность DTEK |
|---|---|
| 0.0 | None (не создаёт риск) |
| 0.1 – 3.9 | low |
| 4.0 – 6.9 | medium |
| 7.0 – 8.9 | high |
| 9.0 – 10.0 | critical |

**Примечание:** CVSS в DTEK Core — это информационный атрибут. Фактическое влияние на Trust Score определяет поле `severity` (критичность), которое устанавливается вручную и может отличаться от CVSS (например, когда контекст организации делает риск менее критичным, чем по CVSS).

## SLA — дедлайны устранения

SLA (Service Level Agreement) в контексте рисков — это максимально допустимое время на устранение риска.

**Как работает SLA в DTEK Core:**

1. Владелец или аналитик указывает календарную дату устранения либо `sla_days`
   (количество календарных дней).
2. Явная дата используется как `due_date`; если она не задана, система
   вычисляет `due_date` от текущей даты и `sla_days`.
3. При изменении даты форма очищает SLA, а при изменении SLA очищает явную дату,
   чтобы у риска оставался один актуальный источник срока.
4. Активный риск отображается как «Просрочено», «Скоро срок» при остатке менее
   трёх дней или «В графике». Для `mitigated`, `accepted` и `closed` SLA-warning
   останавливается и отображается как завершённый.

**Рекомендуемые SLA по критичности:**

| Критичность | SLA | Обоснование |
|---|---|---|
| critical | 1–3 дня | Активная угроза, возможна эксплуатация прямо сейчас |
| high | 7 дней | Серьёзная угроза, высокий риск эксплуатации |
| medium | 14–30 дней | Требует планового устранения |
| low | 90 дней | Информационный риск, можно устранить в плановом режиме |

## Комментарии К Риску

В drawer риска участники организации видят хронологию комментариев. Владелец и
аналитик ИБ могут добавить комментарий длиной до 2000 символов, чтобы
зафиксировать ход устранения или принятое решение. Комментарии неизменяемы:
редактирование и удаление не входят в MVP. Администратор и наблюдатель имеют
только доступ на чтение.

## История Работы С Риском

Блок «История работы» в drawer показывает новые события сверху:

- назначение или снятие ответственного;
- изменение либо снятие срока и SLA;
- изменение статуса;
- добавление комментария.

Для каждого события видны участник, относительное время и безопасный контекст
изменения. История доступна всем ролям организации на чтение, но создаётся
только через разрешённые owner/analyst действия. Она не является журналом
безопасности Audit Log: расширенный security audit реализуется отдельным этапом.

Если ответственный или срок указаны при ручном создании риска, эти начальные
назначения также появляются в истории.

Старые действия, совершённые до включения timeline, не восстанавливаются
предположениями. Для такого риска отображается пустое состояние до первого
нового workflow-события.

## Происхождение Риска

В реестре рядом с идентификатором отображается происхождение риска:

- `Вручную` — риск зарегистрирован участником организации в DTEK Core;
- `Импорт` — риск создан через CSV/XLSX import и имеет source context.

Drawer импортированного риска показывает название и тип источника, дату сбора
и confidence. Эти поля помогают оценить происхождение и актуальность записи,
но не являются отдельной Evidence-записью и не влияют на Trust Score.
`source_record_id` остаётся внутренним metadata и не показывается в UI.

При редактировании импортированного риска форма показывает только обычное
описание. Служебный `[Import Source]` block сохраняется Server Action и не
должен редактироваться пользователем вручную. Если metadata отсутствует или
повреждено, интерфейс использует безопасный статус `Вручную`, не придумывая
источник.

## Привязка рисков к объектам

Один риск может быть привязан к **нескольким объектам** одновременно.

**Пример:** Уязвимость в версии OpenSSL затрагивает одновременно 5 серверов. Создаётся один риск и привязывается к 5 объектам — Trust Score каждого снижается независимо.

**Как привязать риск к объекту:**
1. Откройте страницу объекта `/objects/[id]`
2. Перейдите во вкладку «Риски»
3. Нажмите «Добавить риск» и выберите существующий риск из реестра

**Как отвязать риск:**
- На странице объекта → вкладка «Риски» → удалить привязку (риск остаётся в реестре)

## Влияние риска на Trust Score: детали

**Только активные риски (open, in_progress) снижают Trust Score.** Закрытые, принятые и смягчённые — не влияют.

**Категория риска определяет, какой фактор пострадает:**

```
Риск "CVE-2026-1234 — RCE в nginx" (category: vulnerability, severity: critical)
    → штраф −40 к фактору vuln

Риск "Открыт RDP на сервере" (category: configuration, severity: high)
    → штраф −25 к фактору config

Риск "Слабая парольная политика" (category: access, severity: medium)
    → штраф −15 к фактору access

Риск "Отсутствие сегментации сети" (category: network, severity: high)
    → штраф −25 к фактору network

Риск "Нет политики обработки инцидентов" (category: organizational, severity: medium)
    → штраф −15/6 ≈ −3 к КАЖДОМУ из 6 факторов (равномерное распределение)
```

## Работа с риском: пошаговый процесс

### Создание риска

1. `/risks` → «Добавить риск»
2. Заполните название, выберите категорию и критичность
3. Укажите SLA в днях (обязательно для критических рисков)
4. Добавьте описание с деталями: вектор атаки, потенциальный ущерб, рекомендации по устранению
5. Назначьте ответственного исполнителя
6. Нажмите «Создать»

### Привязка к объектам

1. Откройте нужный объект `/objects/[id]`
2. Вкладка «Риски» → «Добавить риск»
3. Найдите только что созданный риск → привяжите
4. Trust Score объекта пересчитается автоматически

### Работа по устранению

1. Возьмите риск в работу: статус `open` → `in_progress`
   - Trust Score ещё не восстанавливается (штраф всё ещё активен)
2. После принятых мер сменить статус:
   - `mitigated` — если угроза снижена, но не устранена полностью
   - `accepted` — если риск принят как допустимый (документируйте причину в описании)
   - `closed` — если угроза полностью устранена
3. Trust Score пересчитается — штраф снят

## Фильтрация и поиск в реестре

Реестр рисков поддерживает:
- Фильтрацию по **статусу**, **критичности**, **категории**
- Поиск по названию и описанию
- Сортировку по дате создания, критичности, дедлайну SLA

**Рекомендуемые рабочие представления:**
- «Все открытые критические» → sort по due_date → начинать день с них
- «Просроченные» → filter status = open/in_progress, due_date < today
- «Принятые риски» → filter status = accepted → периодически пересматривать

## Импорт Рисков Из CSV/XLSX

Для первичного наполнения реестра роли **Владелец** и **Аналитик ИБ** могут использовать команду **Импорт** на странице `/risks`.

Импорт выполняется в два этапа:

1. Платформа проверяет файл и показывает preview без записи данных.
2. Пользователь подтверждает создание валидных строк.

Обязательные колонки — `title` и `severity`. Риск можно связать с существующим объектом по точному `linked_object_name` или уникальному `linked_object_ip`. Если объект не найден, риск создаётся без связи с warning; Trust Score начнёт учитывать его после ручной привязки.

Импорт работает в режиме create-only: существующие риски не обновляются, ошибки и дубли пропускаются, а остальные валидные строки создаются. Полный формат, шаблон, source metadata и расшифровка ошибок описаны в [IMPORT_GUIDE.md](IMPORT_GUIDE.md).

## Экспорт Risk Registry В CSV

Реестр рисков можно выгрузить в CSV для анализа, согласования remediation-плана или передачи пилотной команде.

**Как экспортировать:**

1. Откройте `/risks`.
2. Примените нужные фильтры по поиску, статусу или критичности.
3. Нажмите **CSV**.
4. Платформа скачает файл `dtek-core-risk-registry-YYYY-MM-DD.csv`.

Экспорт учитывает текущие фильтры интерфейса. Если по фильтрам нет рисков, файл всё равно будет создан с заголовками колонок.

**Доступ:** только роли **Владелец** и **Аналитик ИБ**.

Подробнее: [REPORTS_AND_EXPORT_GUIDE.md](REPORTS_AND_EXPORT_GUIDE.md).
