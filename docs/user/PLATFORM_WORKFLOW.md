# DTEK Core — Рабочий процесс платформы

`Версия: 1.0`  
`Дата: 26.06.2026`

---

## Обзор жизненного цикла

DTEK Core следует единому рабочему процессу, который превращает разрозненные данные о безопасности в управляемую модель доверия. В текущем MVP данные можно вводить вручную; после ADR-007 целевая модель развивается как Evidence-first: импорт и коннекторы становятся основным способом первичного наполнения, а ручная работа — корректировкой и добавлением бизнес-контекста.

Жизненный цикл состоит из 11 этапов:

```
① Создание организации
        ↓
② Приглашение пользователей
        ↓
③ Импорт / создание объектов
        ↓
④ Подтверждение и уточнение модели
        ↓
⑤ Построение Trust Graph (связи)
        ↓
⑥ Регистрация / импорт рисков
        ↓
⑦ Привязка рисков к объектам
        ↓
⑧ Trust Passport — автоматически
        ↓
⑨ Trust Score — автоматически
        ↓
⑩ Работа с реестром рисков (статусы, SLA, evidence)
        ↓
⑪ Аналитика и переоценка доверия
        ↓
   (цикл повторяется при изменениях)
```

---

## Этап 1 — Создание организации

**Кто:** Владелец (первый пользователь системы)  
**Где:** Мастер первичной настройки при первом входе

При первом входе в платформу пользователь создаёт **организацию** — рабочее пространство, которое изолировано от всех других организаций. Все данные: объекты, риски, пользователи — принадлежат конкретной организации.

**Что делается:**
- Вводится название организации
- Создаётся запись в базе данных с уникальным ID
- Пользователю присваивается роль **Владелец (owner)**
- Создаётся начальная конфигурация Trust Score (веса факторов по умолчанию)

**Результат:** Рабочее пространство готово. Dashboard пока пустой — нет объектов и рисков.

---

## Этап 2 — Приглашение пользователей

**Кто:** Владелец
**Где:** `/users` → «Пригласить»

Владелец создаёт приглашение, указывая email коллеги и роль:

| Роль | Что может делать |
|---|---|
| Аналитик ИБ | Создавать и редактировать объекты, риски, связи |
| Администратор | Управлять не-owner участниками и создавать инфраструктурные объекты |
| Наблюдатель | Только просмотр всех данных |

Платформа показывает ссылку приглашения → владелец копирует её и отправляет коллеге вручную → приглашённый переходит по ссылке → выбирает пароль → входит в ту же организацию с назначенной ролью.

**Результат:** Команда сформирована, каждый может начать работу в пределах своей роли.

Важно: если участник команды регистрируется отдельно через `/register`, он создаёт новую организацию и получает роль owner в ней. Для входа в существующую организацию нужно использовать invite-ссылку.

---

## Этап 3 — Импорт / создание объектов

**Кто:** Владелец, Аналитик ИБ, Администратор  
**Где:** `/objects` → «Импорт» или «Добавить объект»

**Объект** — это любой информационный актив, который нужно отслеживать: сервер, приложение, база данных, учётная запись, сетевое устройство, документ политики и т.д.

В текущем MVP объект можно импортировать из CSV/XLSX с source metadata и validation preview. Ручное создание остаётся fallback для единичных объектов и экспертной корректировки. AD/LDAP, Zabbix, MaxPatrol VM, Wazuh, Kaspersky Security Center и другие прямые источники относятся к следующим этапам Connector Framework.

Форматы, роли и пошаговый сценарий: [IMPORT_GUIDE.md](IMPORT_GUIDE.md).

**Что заполняется при создании:**
- Название и тип объекта
- Критичность: `low` / `medium` / `high` / `critical`
- Описание (рекомендуется)
- IP-адрес, платформа, сегмент сети, тип экспозиции (опционально)
- Ответственный владелец

**Что происходит автоматически:**
- Создаётся запись объекта в базе данных
- **Автоматически создаётся Trust Passport** для объекта
- Рассчитывается начальный Trust Score на основе критичности

**Базовые значения по критичности (до учёта рисков):**

| Критичность | Начальный Trust Score |
|---|---|
| Низкая (low) | 80 |
| Средняя (medium) | 75 |
| Высокая (high) | 70 |
| Критическая (critical) | 65 |

**Результат:** В системе появляются объекты с Trust Passport и начальным Trust Score.

---

## Этап 4 — Подтверждение и уточнение модели

**Кто:** Владелец, Аналитик ИБ  
**Где:** в будущем — Discovery Inbox

Автоматически найденные объекты, связи и риски должны проходить подтверждение, если уверенность системы недостаточна.

**Что делает пользователь:**
- подтверждает объект;
- объединяет дубли;
- отклоняет ошибочные candidates;
- назначает владельца;
- уточняет критичность;
- добавляет бизнес-контекст.

**Результат:** цифровая модель остаётся автоматизированной, но контролируемой специалистом ИБ.

---

## Этап 5 — Построение Trust Graph

**Кто:** Владелец, Аналитик ИБ  
**Где:** `/graph` → «Добавить связь»

После создания объектов строится **граф связей** — визуальная модель зависимостей инфраструктуры.

**Типы связей:**

| Тип | Значение | Пример |
|---|---|---|
| `uses` (Использует) | Объект A использует объект B | Приложение использует базу данных |
| `depends_on` (Зависит от) | Объект A зависит от объекта B | Сервис зависит от сервера |
| `connected_to` (Подключён к) | Физическое/сетевое подключение | Сервер подключён к коммутатору |
| `managed_by` (Управляется) | Объект A управляется объектом B | Сервер управляется учётной записью администратора |
| `owns` (Владеет) | Объект A владеет объектом B | Платформа владеет базой данных |
| `interacts_with` (Взаимодействует) | Двустороннее взаимодействие | Сервис взаимодействует с внешним API |

**Зачем строить граф:**
- Видны цепочки доверия: если скомпрометирован один узел, какие объекты пострадают
- Помогает расставить приоритеты при устранении рисков (критичные узлы с множеством связей)
- Визуально демонстрирует сложность инфраструктуры и её уязвимые точки

**Результат:** На экране Trust Graph видна интерактивная карта инфраструктуры с цветовой индикацией уровней доверия.

## Этап 6 — Регистрация / импорт рисков

**Кто:** Владелец, Аналитик ИБ  
**Где:** `/risks` → «Добавить риск»

**Риск** — это угроза, уязвимость или проблема, которая снижает уровень доверия к объектам организации.

В Evidence-first модели риск может быть создан вручную, импортирован из файла или предложен Auto Risk Mapper на основе evidence.

**Что заполняется:**
- Название и описание
- Категория (11 категорий: уязвимость, конфигурация, доступ, сеть, соответствие, инцидент и др.)
- Критичность: `low` / `medium` / `high` / `critical`
- Вероятность реализации: `low` / `medium` / `high`
- CVSS-оценка (0–10, опционально)
- SLA в днях (дедлайн устранения)
- Ответственный исполнитель

**Результат:** Риск зарегистрирован в реестре со статусом `open`.

---

## Этап 7 — Привязка рисков к объектам

**Кто:** Владелец, Аналитик ИБ  
**Где:** На странице объекта `/objects/[id]` → вкладка «Риски»

Риск привязывается к одному или нескольким объектам, которые он затрагивает.

**Что происходит автоматически:**
- Сразу после привязки запускается **пересчёт Trust Score** затронутого объекта
- В Trust Passport обновляются факторные оценки
- Обновляется организационный Trust Index

**Как риск влияет на Trust Score:**

| Критичность риска | Штраф к фактору |
|---|---|
| Критический (critical) | −40 пунктов |
| Высокий (high) | −25 пунктов |
| Средний (medium) | −15 пунктов |
| Низкий (low) | −5 пунктов |

Штраф применяется к соответствующему фактору (категория риска → фактор Trust Score). Если категория риска не привязана к конкретному фактору, штраф распределяется равномерно по всем 6 факторам.

**Результат:** Trust Score объекта снизился, что отражает реальную угрозу.

---

## Этап 8 — Trust Passport (автоматически)

**Кто:** Создаётся системой автоматически  
**Где:** `/objects/[id]/passport`

**Trust Passport** создаётся для каждого объекта автоматически при его добавлении и содержит:

- **Trust Ring** — круговой индикатор Trust Score (0–100)
- **Уровень доверия** — High / Good / Medium / Low / Critical
- **6 факторных оценок** — разбивка Trust Score по факторам
- **Полнота паспорта** — процент заполненности данных об объекте (0–100%)
- **Количество активных рисков** — риски со статусом open/in_progress
- **Реквизиты объекта** — тип, критичность, IP, платформа, сегмент, экспозиция
- **История Trust Score** — все изменения оценки с причинами

**Как повысить Trust Score:** устраняйте риски (меняйте статус на `mitigated`/`closed`) и заполняйте паспорт (чем больше данных, тем выше бонус к фактору «Соответствие ПБ»).

---

## Этап 9 — Trust Score (автоматически)

Trust Score рассчитывается автоматически при каждом из следующих событий:

- Добавление риска к объекту
- Изменение статуса риска (open → in_progress → mitigated → closed)
- Удаление привязки риска к объекту
- Изменение критичности объекта
- Обновление данных объекта (влияет на полноту паспорта)
- Изменение весов факторов в Конфигураторе (пересчитываются все объекты)

**Формула:**
```
Trust Score = Σ (оценка_фактора × вес_фактора) / 100
```

Где каждая оценка фактора = `базовая_оценка − штрафы_за_риски + бонус_за_полноту`

## Этап 10 — Работа с реестром рисков

**Кто:** Владелец, Аналитик ИБ  
**Где:** `/risks`

Основной рабочий процесс аналитика — ведение реестра рисков:

```
open → in_progress → mitigated → closed
         ↓
      accepted (если риск принимается, а не устраняется)
```

**Жизненный цикл статуса:**

| Статус | Значение | Влияние на Trust Score |
|---|---|---|
| `open` | Риск зафиксирован, работа не начата | Штраф применяется |
| `in_progress` | Устранение в процессе | Штраф применяется |
| `mitigated` | Риск снижен (не устранён полностью) | Штраф **снимается** |
| `accepted` | Риск принят (осознанное решение) | Штраф **снимается** |
| `closed` | Риск устранён полностью | Штраф **снимается** |

**Важно:** Trust Score пересчитывается в реальном времени при изменении статуса.

---

## Этап 11 — Аналитика и переоценка

**Кто:** CISO, Владелец, Аналитик ИБ  
**Где:** `/dashboard`

Dashboard предоставляет агрегированную аналитику:

- **Организационный Trust Index** — взвешенное среднее Trust Score всех объектов
- **Топ объектов с наименьшим доверием** — приоритеты для работы
- **Тренд за 30/90/365 дней** — динамика изменений
- **Распределение по уровням** — сколько объектов в каждом уровне доверия
- **Лента событий** — последние изменения в реальном времени

**Переоценка:** Конфигуратор (`/configurator`) позволяет скорректировать веса факторов под специфику вашей отрасли. После сохранения все Trust Score пересчитываются автоматически.

## Полный цикл на примере

> **Сценарий:** Найдена критическая уязвимость в основном сервере приложений.

1. **Аналитик** заходит в `/risks` → создаёт риск «CVE-2026-XXXX — RCE в nginx», категория `vulnerability`, критичность `critical`, SLA 3 дня
2. **Аналитик** открывает `/objects` → находит объект «Сервер приложений» → привязывает риск
3. **Система** автоматически пересчитывает Trust Score сервера: штраф −40 к фактору `vuln`
4. **Dashboard** показывает сервер в топе самых уязвимых объектов, организационный Trust Index снизился
5. **Администратор** обновляет nginx → аналитик меняет статус риска на `mitigated`
6. **Система** снимает штраф → Trust Score восстанавливается
7. **История** паспорта фиксирует оба события: падение и восстановление

**Итог:** Полный цикл управления доверием от обнаружения угрозы до её устранения — задокументирован и измерен.
