# 06. Сквозные пользовательские сценарии

## 1. Создание организации

Пользователь регистрируется → Supabase Auth создаёт user/profile → middleware ведёт на `/onboarding/create` → Server Action валидирует форму → admin client создаёт организацию, привязывает профиль как `owner` и создаёт config → wizard сохраняет веса и приглашения → `/dashboard`.

Защита: действие требует authenticated user; `owner_id` берётся из сессии, секретный ключ остаётся на сервере. Ограничение: компенсационная транзакция для частичного сбоя создания не показана как единая DB transaction.

## 2. Ручное добавление объекта

Пользователь с разрешённой ролью открывает `/objects`, заполняет форму → Zod проверяет данные → action добавляет `organization_id` из профиля → RLS ограничивает tenant → DB-trigger создаёт `trust_passport` → engine рассчитывает score → список revalidate.

Viewer не должен иметь права записи; передаваемый браузером tenant не считается доверенным.

## 3. Импорт объектов

Пользователь скачивает шаблон → выбирает CSV/XLSX до 5 МБ и 500 строк → браузер parser превращает файл в matrix → server preview нормализует заголовки, проверяет значения и дубли → пользователь подтверждает → create-only commit записывает валидные строки и source block → паспорта появляются автоматически.

Partial success означает: успешные строки сохраняются, ошибки выгружаются отдельно. Полного rollback файла и merge/update нет.

## 4. Импорт рисков

Файл проходит тот же pipeline → строки сопоставляются с объектами → валидные риски и связи создаются tenant-scoped → импорт логируется → пересчитываются затронутые объекты.

## 5. Trust Passport

Пользователь открывает объект → report service собирает объект, паспорт, риски, связи, историю и веса только своей организации → UI показывает Score, top drivers, reason cards, source context и ориентировочный эффект рисков.

## 6. Trust Graph

Пользователь видит объекты как вершины и ручные relations как рёбра → owner/analyst может создать связь после проверки принадлежности обоих объектов tenant → canvas показывает зависимость. Автоматического обнаружения связей нет.

## 7. Будущая автоматизация

Источник → connector/collector → raw evidence → normalization → identity resolution → Discovery Inbox → подтверждённый объект → Passport/Score/Graph/risk candidate. Это утверждённая концепция, не текущий пользовательский сценарий.

> Главное, что нужно запомнить: каждый реализованный сценарий должен прослеживаться от действия пользователя до строки БД и проверки доступа.

## Проверь себя

1. Почему объект получает паспорт автоматически?
2. Где импорт может завершиться частично?
3. Какие проверки нужны перед созданием relation?
4. Что в сценарии 7 ещё отсутствует?
